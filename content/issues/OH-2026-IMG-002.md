## Summary

`PostProc::GetCropValue` classifies a crop with bare `int32_t` adds
`top + height` and `left + width`. When the mathematical sum exceeds
`INT32_MAX`, the sum wraps (signed overflow is UB; common compilers wrap) and
often compares `<= size.*` as **true**, so an out-of-image crop is classified
**`CropValue::VALID`**.

`ValidCropValue` only mutates extents when `GetCropValue` returns **`INVALID`**.
On false **`VALID`**, repair never runs — overflow crop is kept. Crafted large
origin can drive **OOB read** on the **left** path. Not hot-path / normal-image
High: origins near `INT32_MAX` are rare; **top-only** overflow tends to skip
rows rather than read past the buffer. Confirmed and fixed by developers
(`DTS2026072438492`).

## Vulnerable Code

`frameworks/innerkitsimpl/converter/src/post_proc.cpp` — `GetCropValue` (~721):

```cpp
bool isValid = ((rect.top >= 0 && rect.width > 0 && rect.left >= 0 && rect.height > 0) &&
                (rect.top + rect.height <= size.height) &&
                (rect.left + rect.width <= size.width));
```

Callers: `NeedScanlineFilter` / `ConvertProc`; `PixelMap::ValidateCropRange` →
`Create`; `ImageSource` via `ValidCropValue`. Downstream: `FilterLine`
(`startPixel = src + left * srcBpp_`); `SourceCropAndConvert` with
`Position{left,top}`.

Root cause: bare int32 origin+extent add. Must widen before add (or use
subtract form like sibling `IsRectInBounds` in `pixel_map_gl_utils.h`).

## Trigger Conditions

1. Caller supplies a crop `Rect` with origin near `INT32_MAX` and positive
   extent (API / decode options), not a typical in-bounds UI crop.
2. `GetCropValue` wraps the sum and returns **VALID**.
3. `ValidCropValue` sees VALID → no clamp; path continues into scanline /
   convert with huge origin.

No upstream guard reliably blocks the witness. `ImageSource::CheckCropRectValid`
is **skipped** when `cropAndScaleStrategy == DEFAULT`; non-default uses
`IsSrcRectContainsDistRect`, which **also** adds in int32 and can mis-accept
the same shape.

## Impact

- False **`VALID`** bypasses `ERR_IMAGE_CROP` / create failure.
- **Left-overflow + in-range top:** scanline / convert path can **read past**
  the source buffer (`FilterLine` / `ReadPixelsConvert`).
- **Top-overflow only:** row filter usually skips all lines → failed/empty
  crop more than classic OOB (do not claim universal OOB for every witness).
- Field likelihood: **low** (origins near `INT32_MAX`); impact when hit:
  **memory-safety / wrong crop** on real APIs that pass `Rect` through.
- Medium: not hot-path High.

## Minimal Counterexample

```
rect = { left=0, top=2147483640, width=1, height=100 }
size = { width=100, height=100 }

// int32: 2147483640 + 100 wraps → negative; (wrapped <= 100) true
Production GetCropValue → VALID     // bug
Expected                 → INVALID

// left+width (OOB-relevant):
rect = { left=2147483640, top=0, width=100, height=1 }
Production GetCropValue → VALID     // bug
// FilterLine: startPixel = src + left * bpp  → past buffer if path runs
```

## How PBT Detected This

`pbt-native/get_crop_value_overflow_pbt_test` — host-linked real `post_proc.cpp`:

| Test | Result |
|------|--------|
| `OverflowAddNeverValid` | **FAIL** |
| `ValidCropValueRejectsOverflow` | **FAIL** |
| `FixedOverflowWitness` | **FAIL** (VALID vs INVALID) |

```bash
cmake -S pbt-native -B pbt-native/build -DCMAKE_BUILD_TYPE=Release
cmake --build pbt-native/build -j --target get_crop_value_overflow_pbt_test
./pbt-native/build/get_crop_value_overflow_pbt_test
```

## Suggested Fix

Widen before add:

```cpp
const bool isValid =
    rect.top >= 0 && rect.left >= 0 && rect.width > 0 && rect.height > 0 &&
    static_cast<int64_t>(rect.top) + rect.height <= size.height &&
    static_cast<int64_t>(rect.left) + rect.width <= size.width;
```

Same widen in `ValidCropValue` repair compares. Optional sibling:
`IsSrcRectContainsDistRect` (`image_source.cpp`) uses the same int32 add
pattern — fix in one ticket if filing together.

After fix: `OverflowAddNeverValid`, `ValidCropValueRejectsOverflow`,
`FixedOverflowWitness` → PASS.
