## Summary

`Disassembler::GetParams` indexes its fill loop with `uint8_t i` while
comparing against `uint32_t params_num` (bounded by `MAX_ARG_NUM = 0xFFFF`).
When `params_num ∈ [256, 65535]`, `i` wraps at 255 → `i < params_num` is
**perpetually true** → eternal loop and unbounded `method->params` growth
until OOM.

Offline tooling DoS on well-formed abc (`ark_disasm` /
`Disassembler::Disassemble`). Likelihood on normal source is extremely low
(need ≥256 formals); certain on crafted/fuzzed abc. Confirmed and fixed by
developers (`DTS2026071433052`).

## Vulnerable Code

`disassembler/disassembler.cpp` — `Disassembler::GetParams` (~757):

```cpp
auto params_num = code_accessor.GetNumArgs();   // uint32_t
if (params_num > MAX_ARG_NUM) { ... return; }   // MAX_ARG_NUM = 0xFFFF
for (uint8_t i = 0; i < params_num; i++) {      // <-- uint8_t loop index
    method->params.push_back(...);
}
```

Sibling footgun: `Serialize` (~1937) also used `for (uint8_t i = 1; i < method.params.size(); i++)` — harmless while GetParams never filled ≥256; becomes wrong after a GetParams-only fix.

Root cause: `uint8_t` index contradicts the SUT’s own contract to support up to
65535 args (`MAX_ARG_NUM` comment: “frame size - 2^16 - 1”).

## Trigger Conditions

1. Well-formed `.abc` with a CODE item declaring `num_args ∈ [256, 65535]`.
2. `Disassembler::Disassemble` → `GetMethod` → `GetParams` runs the fill loop.
3. `uint8_t i` wraps; loop never exits; `method->params` grows unboundedly.

Unaffected: `params_num ∈ [0, 255]` (correct); `params_num > 65535` (early
return). Not blocked by callers — no pre-clamp; assembler allows large
formals; only gate is in-function `> 0xFFFF`.

## Impact

| Axis | Rating |
|------|--------|
| Impact when hit | High (infinite loop + memory growth in `GetParams`) |
| Likelihood on normal source / CI abc | Extremely low (need ≥256 declared formals) |
| Likelihood on crafted / fuzzed abc | High (any `num_args ∈ [256, 65535]`) |
| Path | Offline tooling (`ark_disasm` / `Disassembler`), not interpreter execute |
| Overall | **Medium** |

Empirical in-tree: ~6.4k `.function` declarations — max **252** formals; hang
band never hit accidentally. Runtime execute does not use this loop.

## Minimal Counterexample

```
N = 256 parameters
.function any f(any a0, …, any a255) { return }

AsmEmitter::Emit succeeds; CodeDataAccessor::GetNumArgs() == 256
Disassembler::Disassemble does not return
→ forked child hits 6s SIGALRM → status = TIMEOUT

Contrast: N ∈ [0, 255] round-trip exactly (PropBoundary255 PASS)
```

## How PBT Detected This

`pbt-native/disasm_getparams_pbt_test` — real compiled `arkdisassembler`
closure via public API `Disassemble → GetMethod → GetParams → Serialize`:

| Property | Result |
|----------|--------|
| `PropBoundary256` (P3) | **FAIL** (`TIMEOUT`) |
| `PropBoundary255` / `PropSmallNExact` / `PropNoCrash` | PASS |

```bash
bash pbt-native/disasm_build_libs.sh
./pbt-native/build/disasm_getparams_pbt_test
# P3 N=256: status=1 (TIMEOUT)
```

## Suggested Fix

Widen loop indices to match `params_num` / container size (as implemented):

```cpp
for (uint32_t i = 0; i < params_num; i++) {
    method->params.push_back(...);
}
// Serialize sibling: size_t i
```

`MAX_ARG_NUM` already bounds `params_num ≤ 65535`, so a 32-bit index cannot
overflow under the existing guard.
