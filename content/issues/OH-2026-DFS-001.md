## Summary

`ChangesResult::ReadFromParcel` loops over parcel items and calls
`changeData.ReadFromParcel(parcel)` but **discards the bool**. On any sub-field
read failure it still `push_back`s a default/partial `ChangeData` and returns
`true`. Outer `Unmarshalling` therefore yields a successful object with garbage
entries instead of `nullptr`.

Same-file `Marshalling` already propagates item failure; `Unmarshalling`
already aborts when outer `ReadFromParcel` returns false. Confirmed and fixed
by developers (`DTS2026072326318`).

## Vulnerable Code

`frameworks/native/clouddiskservice_kit_inner/src/cloud_disk_common.cpp` —
`ChangesResult::ReadFromParcel` (~207):

```cpp
for (int32_t i = 0; i < size; ++i) {
    ChangeData changeData;
    changeData.ReadFromParcel(parcel);   // bool ignored
    changesData.push_back(changeData);   // always push
}
return true;
```

`ChangeData::ReadFromParcel` (~124) returns `false` on any sub-field `Read*`
failure. Caller: `ChangesResult::Unmarshalling` → client IPC
`CloudDiskServiceManagerImpl::GetSyncFolderChanges`.

Root cause: discarded item-reader return; unconditional push.

## Trigger Conditions

1. Client unmarshalls a `GetSyncFolderChanges` reply via
   `ChangesResult::Unmarshalling`.
2. Parcel has a valid size/header but a truncated/corrupt item mid-loop
   (e.g. `fileId` `ReadString` fails).
3. Item `ReadFromParcel` returns false; loop still pushes and outer read
   returns true → successful unmarshall with partial entries.

## Impact

- Caller sees successful unmarshall with garbage entries (zero USN, empty ids,
  etc.) instead of failure.
- Producer is the trusted local `CloudDiskService`; request `count` capped at
  `GET_SYNC_FOLDER_CHANGE_MAX` (100). Well-formed trusted replies do not hit
  the path.
- Defect is live only on malformed/truncated parcels — still a real
  IPC-boundary contract bug (silent accept).
- Medium not High: no unbounded alloc on this residual; no remote
  attacker-shaped input on the normal service path; wrong data quality on
  corruption, not crash/UB.

## Minimal Counterexample

```
parcel: nextUsn ok | isEof ok | size=1 | ChangeData truncated (e.g. fileId ReadString fails)

Production:  push default/partial ChangeData; ChangesResult::ReadFromParcel → true
Expected:    do not push; ChangesResult::ReadFromParcel → false
             (Unmarshalling then yields nullptr)
```

encodes the discarded-bool path (behavioral model, not linked SUT):

| Check | Result |
|-------|--------|
| Source: bool discarded at loop | Yes |
| `B1_02` production vs secure | **FAIL** (documents gap) |

cmake -B pbt-native/build pbt-native
cmake --build pbt-native/build -j --target batch1_residuals_pbt_test

## Suggested Fix

Mirror `Marshalling` / other bool parcel loops:

```cpp
for (int32_t i = 0; i < size; ++i) {
    ChangeData changeData;
    if (!changeData.ReadFromParcel(parcel)) {
        LOGE("failed to read changeData at index %{public}d", i);
        return false;
    }
    changesData.push_back(changeData);
}
```

After fix: residual model `FailedReadMustReject` flips PASS; do not push
partial item; outer `ReadFromParcel` returns `false`.
