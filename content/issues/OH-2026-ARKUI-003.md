## Summary

`Matrix4::SetEntry(row, col, value)` writes to `matrix4x4_[row][col]`, but `Matrix4::Get(row, col)` and `Matrix4::Set(row, col, value)` read/write `matrix4x4_[col][row]`. Off-diagonal writes therefore do not round-trip: a value written to logical cell `(1, 0)` is read back from the transposed slot `(0, 1)` instead of the same logical cell.

Fix landed in PR: `https://gitcode.com/openharmony/arkui_ace_engine/pull/86313`.

## Contract

From `frameworks/base/geometry/matrix4.h`:

```cpp
// line 68
void SetEntry(int32_t row, int32_t col, double value);

// line 86
inline double Get(int32_t row, int32_t col) const
{
    ACE_DCHECK((unsigned)row < DIMENSION);
    ACE_DCHECK((unsigned)col < DIMENSION);
    return matrix4x4_[col][row];
}

// line 92
inline void Set(int32_t row, int32_t col, double value)
{
    ACE_DCHECK((unsigned)row < DIMENSION);
    ACE_DCHECK((unsigned)col < DIMENSION);
    matrix4x4_[col][row] = value;
}
```

Required behavior: after setting a valid logical cell `(row, col)`, reading the same logical cell with `Get(row, col)` must return the written value. `SetEntry` is part of the same logical-cell API as `Get`/`Set`, so it must use the same storage order.

## Vulnerable Code

```cpp
void Matrix4::SetEntry(int32_t row, int32_t col, double value)
{
    if ((row < 0 || row >= DIMENSION) || (col < 0 || col >= DIMENSION)) {
        return;
    }
    matrix4x4_[row][col] = value;   // BUG: opposite storage order from Get/Set
}
```

## Root Cause

`SetEntry` indexes storage as `[row][col]`, while `Get` and `Set` index storage as `[col][row]`. The two storage orders agree only on the diagonal (`row == col`), so off-diagonal `SetEntry` writes land in the transposed slot. The sole production caller is `Matrix4N::operator*`, which builds its result via `SetEntry(i, j, value)` and therefore produces a transposed result for off-diagonal cells.

## Minimal Counterexample

```cpp
Matrix4 matrix = Matrix4::CreateIdentity();
matrix.SetEntry(1, 0, -50);
double value = matrix.Get(1, 0);

// Expected: -50
// Actual:   0   (the -50 was written to matrix4x4_[0][1], read back from matrix4x4_[0][1] == 0)
```

## When the Bug Triggers

- **Does not trigger** for diagonal writes: `SetEntry(0, 0, v); Get(0, 0)` returns `v`, because `[row][col] == [col][row]` on the diagonal.
- **Triggers** for any off-diagonal round-trip: `SetEntry(row, col, v); Get(row, col)` returns the value of the transposed slot whenever `row != col` and the two slots differ.
- **Triggers** in `Matrix4N::operator*`, which constructs its result matrix through `SetEntry`.

## Existing Oracle in Unit Tests

`test/unittest/base/matrix4_test.cpp:148-149`:

```cpp
matrix4Obj1.SetEntry(VALID_ROW0, VALID_COL0, DEFAULT_DOUBLE2);
EXPECT_DOUBLE_EQ(matrix4Obj1.Get(VALID_ROW0, VALID_COL0), DEFAULT_DOUBLE2);
```

This oracle only checks the diagonal `(0, 0)`, so it cannot distinguish `matrix4x4_[row][col]` from `matrix4x4_[col][row]`. Diagonal cells map to the same slot under both storage orders, so the bug is invisible to it.

## Why Existing Tests Missed It

The only round-trip oracle in the suite used the diagonal cell `(0, 0)`. Off-diagonal `SetEntry`/`Get` pairs were never exercised, so the storage-order mismatch had no example that could fail.

## How PBT Detected It

The PBT property in `pbt-native/matrix4_pbt_test.cpp:289-296` encoded the logical-cell contract directly and let RapidCheck generate arbitrary `(row, col, value)` triples:

```cpp
Matrix4 matrix = Matrix4::CreateIdentity();
matrix.SetEntry(row, col, value);
RC_ASSERT(Near(matrix.Get(row, col), value));
```

The failing case shrank to the minimal counterexample:

```text
row = 1
col = 0
value = -50
```

## Impact

- Silent wrong matrix cell update in `Matrix4N::operator*` (the sole production caller)
- Off-diagonal results transposed, no crash and no NAPI exposure at the `SetEntry` boundary
- Diagonal paths unaffected, so the bug is easy to miss

## Suggested Fix

Make `SetEntry` use the same storage order as `Get` and `Set`:

```cpp
void Matrix4::SetEntry(int32_t row, int32_t col, double value)
{
    if ((row < 0 || row >= DIMENSION) || (col < 0 || col >= DIMENSION)) {
        return;
    }
    matrix4x4_[col][row] = value;
}
```

## Verification

Confirmed by:
- explicit `Get`/`Set` contract in `matrix4.h`
- the diagonal-only round-trip oracle that masked the bug
- PBT counterexample at `row=1, col=0, value=-50`
- upstream fix in PR `86313`
