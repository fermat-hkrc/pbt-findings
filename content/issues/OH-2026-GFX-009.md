## Summary

`RSColor` stores sRGB/P3 channels as `int16_t` and BT2020 as **float16 in the
same union**. `GetBlue()` (and siblings) decode BT2020 back to a 0–255 count.
`IsNearEqual`’s same-gamut arm subtracts the raw union fields (`red_`, …).
On BT2020 those are float16 bit patterns, not channel counts.

Animation settle (`RSRenderAnimatableProperty<Color>::IsNearEqual`) passes an
`int16_t` threshold in **channel counts**. A 1-count BT2020 delta can exceed
that threshold in bit space → settle never fires. Confirmed and fixed by
developers (`DTS2026082261311`).

## Vulnerable Code

`rosen/modules/render_service_base/src/common/rs_color.cpp` —
`RSColor::IsNearEqual` (~97):

```cpp
return (std::abs(red_ - other.red_) <= threshold) &&
       (std::abs(green_ - other.green_) <= threshold) &&
       (std::abs(blue_ - other.blue_) <= threshold) &&
       (std::abs(alpha_ - other.alpha_) <= threshold) && ...
```

On BT2020, `blue_` is the float16 bits of `1/255`, not `1`.

`GetBlue()` already documents the decode:

```cpp
if (GetColorSpace() == GRAPHIC_COLOR_GAMUT_BT2020) {
    return round(GetBlueF() * RGB_MAX_VALUE);
}
return blue_;
```

Caller: `RSRenderAnimatableProperty<Color>::IsNearEqual`
(`rs_render_property.cpp` ~775) casts `zeroThreshold` to `int16_t` channel
counts. Spring / interpolating-spring uses that settle test.

Root cause: same-gamut arm compares union storage, not caller-visible
`GetRed()` / `GetGreen()` / `GetBlue()` / `GetAlpha()`. The mismatched-gamut
arm already uses `GetRedF()` + a float threshold.

## Trigger Conditions

1. Same-gamut BT2020 / HDR color property animation.
2. Current and target differ by a small channel-count delta (e.g. 1).
3. `IsNearEqual` compares float16 bits; `|bit_delta| > threshold` even though
   `|GetBlue() - other.GetBlue()| <= threshold`.
4. Spring settle never fires → animation stays logically unfinished.

sRGB `(0,0,0)` vs `(0,0,1)` with threshold 1 is still true (integer storage).

## Impact

- HDR / BT2020 color animation may never settle on a last-count difference.
- Not crash/OOB. Medium: wrong equality on the live animation settle path.
- sRGB/P3 same-gamut compares are unaffected.

## Minimal Counterexample

```cpp
RSColor a(0, 0, 0, 0, GRAPHIC_COLOR_GAMUT_BT2020);
RSColor b(0, 0, 1, 0, GRAPHIC_COLOR_GAMUT_BT2020);
a.IsNearEqual(b, 1);
// Expected: true  (|GetBlue| = 1)
// Actual:   false (float16 bit delta > 1)
```

## How PBT Detected This

`pbt-native/rs_color_isnearequal_pbt_test`:

Oracle: `IsNearEqual` ≡ `Vector4(GetRGBA).IsNearEqual` (sibling `ROSEN_EQ`).

| Case | Result (pre-fix) |
|------|--------|
| `Bt2020AgreesWithGetChannelRosenEq` | **FAIL** |
| `test_IsNearEqual_regression_bt2020_one_count` | **FAIL** |
| sRGB same pair / `AgreesWithVector4Channels` | PASS |

```bash
cmake -S pbt-native -B pbt-native/build -DCMAKE_BUILD_TYPE=Release
cmake --build pbt-native/build -j --target rs_color_isnearequal_pbt_test
./pbt-native/build/rs_color_isnearequal_pbt_test
```

## Suggested Fix

Same-gamut arm must use decoded channel counts:

```cpp
return (std::abs(GetRed() - other.GetRed()) <= threshold) &&
       (std::abs(GetGreen() - other.GetGreen()) <= threshold) &&
       (std::abs(GetBlue() - other.GetBlue()) <= threshold) &&
       (std::abs(GetAlpha() - other.GetAlpha()) <= threshold) &&
       (placeholder_ == other.placeholder_) &&
       OHOS::ColorManager::FloatNearlyEqual(
           GetHeadroom(), Float16ToFloat32(other.headroom_));
```

sRGB unchanged. BT2020 compares 0–255 counts like the animation threshold.

After fix: `Bt2020AgreesWithGetChannelRosenEq` → PASS;
`test_IsNearEqual_regression_bt2020_one_count` → PASS.
