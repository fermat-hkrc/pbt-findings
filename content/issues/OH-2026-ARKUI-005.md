## Summary

`LazyGridLayoutInfo::UpdatePosMapStart()` recalculates the position anchor for the start of the cached lazy-grid position map. When the map starts at index > 0 and has no predecessor entry, the first-branch formula uses only `estimateItemSize_` and omits `spaceWidth_`:

```cpp
prevPos = (updatedStart / lanes_) * estimateItemSize_;
```

The correct row position is `line × (estimateItemSize_ + spaceWidth_)`. Missing the gap term makes item positions drift by `line_number × spaceWidth_` whenever the position map is rebased from a non-zero start index.

## Contract

`docs/pattern/lazy_layout/LazyGrid_Knowledge_Base.md:768` documents the lazy-grid state model: each row starts at `row_index × (estimateItemSize_ + spaceWidth_)`.

The same source file uses that formula in sibling code paths:

```cpp
float estSize = LineCount(prevIndex, totalItemCount_ - 1) * (estimateItemSize_ + spaceWidth_);
```

and:

```cpp
prevPos += (LineCount(prevIndex, it->first) - 1) * (estimateItemSize_ + spaceWidth_);
```

`UpdatePosMapStart()` first-branch is the only path that omits `spaceWidth_`.

## Vulnerable Code

`frameworks/core/components_ng/pattern/lazy_grid_layout/lazy_grid_layout_info.cpp:48-52`:

```cpp
} else {
    prevPos = (updatedStart / lanes_) * estimateItemSize_;   // BUG: missing spaceWidth_
}
```

This branch fires when `startIter == posMap_.begin()`, meaning the cached position map has no entry before `updatedStart`. That is a normal incremental-scroll state when earlier items are off-screen and not in `posMap_`.

## Minimal Counterexample

```text
lanes_ = 2
estimateItemSize_ = 100
spaceWidth_ = 10
updatedStart = 4
line = 4 / 2 = 2
```

Current result:

```text
prevPos = 2 * 100 = 200
```

Expected result:

```text
prevPos = 2 * (100 + 10) = 220
```

The layout anchor is off by `20`, equal to `2 * spaceWidth_`.

## When the Bug Triggers

Any `UpdatePosMap()` call where:

- `posMap_` does not contain entries before `updatedStart_`
- `updatedStart_ / lanes_ > 0`
- `spaceWidth_ > 0`

The error grows with scroll distance because each skipped line loses one gap.

## How PBT Detected This

The PBT suite asserted the line-position invariant for lazy-grid position rebasing:

| Property | Test | Result |
|---|---|---|
| Line-position invariant | `UpdatePosMapStart_LinePositionInvariant` | FAIL |
| Minimal counterexample | `UpdatePosMapStart_MinimalCounterexample` | FAIL |
| Consecutive line spacing | `UpdatePosMapStart_ConsecutiveLineSpacing` | PASS |
| Zero-space regression guard | `UpdatePosMapStart_ZeroSpace_LinePositionCorrect` | PASS |

The failing BugDocs case reproduces the missing gap term directly:

```text
LazyGridLayoutInfoPbt_BugDocs.UpdatePosMapStart_MissingSpaceWidth — FAILED
  startPos=200, expected=220 (missing 2 * spaceWidth_=10)
```

## Impact

Lazy-grid item positions drift by `line_number × spaceWidth_` after rebasing from a non-zero start index. Items can scroll to visually wrong positions, especially after many rows where the accumulated missing gaps become large.

## Suggested Fix

Use the same row-position formula as the rest of the file:

```cpp
prevPos = (updatedStart / lanes_) * (estimateItemSize_ + spaceWidth_);
```
