## Summary

`PasteboardService::SetCurrentDistributedData` runs its distributed-publish pipeline
inside a worker lambda guarded by the `setDistributedMemory_.isRunning` flag. The
flag is an ownership latch: the worker sets it `true` on entry, and later callers
that see `isRunning` **bail out early** (`if (isRunning) return;`) instead of
spawning a new worker. The normal exit path (caught up, or `latestData == nullptr`)
clears the flag with `isRunning = false` before `break`.

The timeout path does not. When the 40s `block->GetValue()` times out, the code hits
`PASTEBOARD_CHECK_AND_RETURN_LOGE(ret, ...)`, which **returns from the lambda without
clearing `isRunning`**. The worker stops, but the flag stays `true` permanently. From
that point on, every `SetDistributedData` sees `isRunning == true`, skips starting a
worker, and the paste is never published to remote peers — cross-device clipboard sync
is dead until the pasteboard service is restarted.

Local paste still works; only the distributed-set path is permanently disabled.

Confirmed and fixed under `DTS2026072000001`. Fix merged in
[MR !2068](https://gitcode.com/openharmony/distributeddatamgr_pasteboard/merge_requests/2068).

## Vulnerable Code

`services/core/src/pasteboard_service.cpp` — `SetCurrentDistributedData` worker:

```cpp
{
    lock;
    latestEvent / latestData = ...;
    if (isRunning) return;        // later callers bail here
    isRunning = true;
}
while (true) {
    ...
    spawn SetCurrentData on innerThread;
    bool ret = block->GetValue();            // 40s timeout
    PASTEBOARD_CHECK_AND_RETURN_LOGE(ret, ..., "timeout,seqId=...");
    // ^^^ on false: RETURN without isRunning = false
}
// normal exit clears the flag:
if (caughtUp || latestData == nullptr) {
    latestData = nullptr;
    isRunning = false;
    break;
}
```

`PASTEBOARD_CHECK_AND_RETURN_LOGE` on a timeout `ret == false` returns immediately,
skipping the only `isRunning = false` reset that lives on the loop's normal `break`
path. One slow encode/plugin stall (large paste, slow delay expand) latches the flag
for the life of the process.

## Trigger Conditions

1. A paste triggers a distributed publish; the worker sets `isRunning = true`.
2. The inner `SetCurrentData` call exceeds the 40s timeout (large payload, slow
   `DelayExpand`, or a plugin encode stall).
3. `block->GetValue()` returns `false`; `CHECK_AND_RETURN_LOGE` returns from the
   worker without clearing `isRunning`.
4. Every subsequent `SetDistributedData` sees `isRunning == true` and returns early —
   no new worker is ever spawned. Remote peers never receive new clips.

No recovery short of restarting the pasteboard service.

## Impact

- **Cross-device clipboard publish permanently disabled** after a single 40s timeout.
  Local set keeps working; distributed sync is a no-op.
- Matches the field symptom class "paste not syncing to other devices until reboot."
- **High:** core distributed feature, single-event permanent failure, no in-band
  recovery, no error surfaced to the caller (the publish silently becomes a no-op).

## How PBT Detected This

A RapidCheck state-machine model (`set_distributed_running_gate_pbt_test`) compared
the production `isRunning` gate against a correct model where any worker stop
(success / no-data / **timeout**) clears the flag. 4 of 6 properties fail:

| Property | Result |
|---|---|
| `TimeoutClearsRunning` | **FAIL** |
| `TimeoutDoesNotStickProduction` | **FAIL** |
| success / OK-step properties | PASS |

Shrunk witnesses:

```
TimeoutClearsRunning
  start isRunning=true, outcome=TIMEOUT
  correct.isRunning   = false  → can start a new worker
  production.isRunning = true  → stuck

TimeoutDoesNotStickProduction
  production after TIMEOUT: CanStartNewWorker == false
```

DONE / OK outcomes still agree — only the timeout error path is mishandled.

## Suggested Fix

Clear `isRunning` on the timeout path before returning (mirror the loop's normal
exit cleanup), or `break` after clearing instead of `return`:

```cpp
bool ret = block->GetValue();
if (!ret) {
    std::lock_guard<std::mutex> lock(setDistributedMemory_.mutex);
    setDistributedMemory_.isRunning = false;
    PASTEBOARD_HILOGE(PASTEBOARD_MODULE_SERVICE, "timeout,seqId=...");
    return;
}
```

Root cause is a missing cleanup on an error path, not the timeout itself — the fix is
the single reset the normal exit already performs.
