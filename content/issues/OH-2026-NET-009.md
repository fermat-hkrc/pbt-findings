## Summary

`StrToInt`, `StrToUint`, and `StrToUint64` called `strto*(…, 0)`. Base `0` is C
auto-detect: a leading `0` means octal. `"08"` → `0` (leftover `8` ignored);
`"010"` → `8`. Quota `"M08"` failed `IsValidPeriodDuration`.

Sibling `ParseInt` already used `strtoll(..., 10)`. Confirmed and fixed under
`DTS20260717048` (upstream `21584d87f` switched these three to `std::from_chars`).
Same commit as `StrToUint64` minus wrap (`OH-2026-NET-008` / `DTS2026071727054`).

`StrToLong` / `StrToBool` still use base `0`; not this ticket.

## Vulnerable Code

Old helpers (`netmanager_base_common_utils.cpp`):

```cpp
int64_t result = std::strtol(value.c_str(), &pEnd, 0);  // same 0 on Int/Uint/Uint64
```

Caller `net_policy_traffic.cpp` `IsValidPeriodDuration`:

```cpp
int32_t start = CommonUtils::StrToInt(periodDuration.substr(1));
```

`"M08"` → `StrToInt("08")` → `0` → `start >= PERIOD_START` fails.

## Trigger Conditions

Decimal strings with a leading `0` that are not meant as octal: `"08"`, `"010"`,
quota day `"M08"` / `"D08"`. Ports, MTU, Content-Length, quota day are decimal.

## Impact

Medium — wrong integer (0 or octal 10) on a decimal field. `"M08"` rejected as
an invalid period. Official tests only used `"M1"`.

## Minimal Counterexample

```
StrToInt("08", -1)     // old 0; now 8
StrToInt("010", -1)    // old 8; now 10
StrToUint("08", 0)     // same
StrToUint64("08", 0)   // same
```

## How PBT Detected This

`pbt-native/str_to_{int,uint,uint64}_pbt_test.cpp`

Algebraic `StrToInt(zeros + to_string(n)) == n` vs `from_chars` base 10.
Witness `"08"`. After `from_chars`: leading-zero properties **PASS**.

## Suggested Fix

Shipped as `from_chars` (`21584d87f`):

```cpp
int32_t result = 0;
auto [ptr, ec] = std::from_chars(value.data(), value.data() + value.size(), result);
if (ec != std::errc{} || ptr != value.data() + value.size()) {
    return defaultErr;
}
return result;
```

Decimal, leftover checked. Same pattern on Uint / Uint64.
