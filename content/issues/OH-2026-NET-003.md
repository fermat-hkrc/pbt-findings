## Summary

`match_loopback` in the eBPF netfirewall connection-tracking path computes a
local `is_loopback` flag (from a `PROTOCOL_SAT_EXPAK && ifindex == 1` special
case, or an src/dst lookup in the `LOOP_BACK_IPV4_MAP` / `LOOP_BACK_IPV6_MAP`
LPM maps populated with `127.0.0.1` and `::1`), and then **throws it away**:

```cpp
static __always_inline bool match_loopback(struct match_tuple match_tpl)
{
    bool is_loopback = false;
    // ... set is_loopback from maps / special case ...
    return true;          // ← bug; should be: return is_loopback;
}
```

The function unconditionally returns `true` — for public Internet flows
(`8.8.8.8`, `1.1.1.1`) as well as real loopback. `match_loopback(tuple)` is the
4th argument of `ct_map_lookup_entry` on both the ingress and egress firewall
hot paths, so the always-true value is applied to every packet while the
netfirewall feature is enabled.

Because the eBPF CT consumer takes the loopback branch whenever a flow is
`CT_NEW`, every new flow does a reverse-tuple re-lookup — and if that reverse
entry exists or resolves as related, the packet returns `SK_PASS` **without
evaluating the deny/allow rule bitmaps**. Net effect: non-loopback traffic can
short-circuit past firewall deny rules, and CT directionality is corrupted for
all traffic.

Upstream one-line fix merged in PR #4561 (`return true` → `return is_loopback`).

## Vulnerable Code

`services/netmanagernative/bpf/include/netfirewall/netfirewall_match.h:147-181`:

```cpp
static __always_inline bool match_loopback(struct match_tuple match_tpl)
{
    bool is_loopback = false;
    // ... sets is_loopback from maps / special case ...
    return true;   // line 181 — always true; should be `return is_loopback`
}
```

Call chain on every ingress/egress firewall decision:

```
netfirewall_ingress / netfirewall_egress          (netfirewall.h)
  → ct_map_lookup_entry(skb, &ct_tpl, dir, match_loopback(tuple))   // netfirewall_ct.h
       status = ct_lookup_entry(...)
       if (status == CT_NEW && is_loopback) {   // always taken when CT_NEW
           swap_ct_tuple_addrs(tuple);
           swap_ct_tuple_ports(tuple);
           status = ct_lookup_entry(...);       // reverse-direction re-lookup
       }
  → if (status != CT_NEW) return SK_PASS;       // skip firewall rules
  → match_action_key / rule evaluation
```

The always-true `is_loopback` has three consequences:

1. Every `CT_NEW` flow performs a reverse-tuple re-lookup (extra BPF map ops;
   wrong for non-loopback).
2. If that reverse entry exists (or is found as related), `status` becomes
   non-`CT_NEW` and the packet returns `SK_PASS` **without evaluating the
   deny/allow bitmaps** — a firewall deny rule for that uid/app/addr is skipped.
3. Loopback-only CT pairing logic is applied to all traffic, merging unrelated
   connections into one CT entry so a later packet of a different flow is
   treated as already allowed.

### Secondary latent bug (not fixed by PR #4561)

The IPv6 branch looks up `daddr` in **`LOOP_BACK_IPV4_MAP`** instead of
`LOOP_BACK_IPV6_MAP`, so even a corrected `return is_loopback` would never
classify `::1 → ::1` via the map path. PR #4561 only fixes the return; this
remains open.

## Trigger Conditions

1. Netfirewall feature is enabled; a packet reaches the BPF ingress/egress
   program (any flow — TCP/UDP, any family, any address).
2. `match_loopback(tuple)` is evaluated as the CT-consumer argument and returns
   `true` regardless of address.
3. For `CT_NEW` flows, the forced reverse-tuple re-lookup may resolve an entry;
   `status` becomes non-`CT_NEW`, and the packet is passed without rule
   evaluation.

No special PAC/config required; the bug fires on every packet while the feature
is on.

## Impact

- **Firewall deny-rule bypass via CT short-circuit.** A DENY rule for
  uid/app/addr is only evaluated when `status == CT_NEW`. Forcing the loopback
  reverse-lookup path can make non-loopback packets resolve as
  established/related and skip the deny path entirely (`return SK_PASS`).
- **CT state confusion.** Reverse-tuple swaps on non-loopback flows can merge
  unrelated connections into one CT entry, so a later packet of a different
  flow is treated as already allowed.
- **Performance.** Extra CT map lookups on every new non-loopback flow.
- **High:** the netfirewall BPF security mechanism is defeated for a class of
  flows; the always-true predicate is not debug dead code — it is on the hot
  path of every ingress/egress decision.

## Minimal Counterexample

```cpp
// Non-loopback public flow
match_tuple t = {
    .family   = AF_INET,
    .protocol = IPPROTO_TCP,   // 6
    .ifindex  = 2,
    .ipv4     = { .saddr = 8.8.8.8, .daddr = 1.1.1.1 },
};
match_loopback(t);   // Expected: false   Actual: true
```

With the intended body (`return is_loopback`) the same input is `false` because
neither endpoint is in `LOOP_BACK_IPV4_MAP`.

## How PBT Detected This

A host-side model of `match_loopback` + the `LOOP_BACK_*` maps (only
`127.0.0.1` / `::1`), preserving the buggy `return true`. Reference oracle is
the same body with `return is_loopback`.

| Property | Result |
|---|---|
| `AgreesWithReferenceOnIpv4` | ❌ FAIL |
| `NonLoopbackIpv4IsFalse` | ❌ FAIL |
| `RealIpv4LoopbackIsTrue` (ref) | ✅ PASS |
| `NonLoopbackIpv6IsFalse` | ❌ FAIL |
| `SatExpakIfindex1IsLoopback` (ref) | ✅ PASS |
| `BugDocs.AlwaysTrue_KnownBug` | ❌ FAIL |
| `BugDocs.RealLoopbackStillTrue` | ✅ PASS |
| `BugDocs.PublicInternetMustNotBypassFirewall` | ❌ FAIL |

Shrunk / deterministic witnesses:

```
MatchLoopbackSut({AF_INET, TCP, if=2, 8.8.8.8 → 1.1.1.1})        → true  (expect false)
MatchLoopbackSut({AF_INET, TCP, if=3, 192.168.0.2 → 93.184.216.34}) → true
MatchLoopbackSut({AF_INET, UDP, if=3, 10.0.0.5 → 8.8.8.8})       → true
MatchLoopbackRef(same)                                            → false
```

RapidCheck fails on trial 1 for every non-loopback property — the bug does not
depend on address bits.

### Why existing tests did not catch this

- `match_loopback` is a `static __always_inline` in a BPF header; no userspace
  unit test invokes it.
- Firewall unit tests exercise rule-install / map-write paths
  (`WriteLoopBackBpfMap`) but not the classification predicate.
- The always-true return is a one-token typo that type-checks and "works" for
  real loopback (`true` is a superset of the correct answer), so loopback-only
  smoke tests stay green.

## Suggested Fix

One-line change (merged in PR #4561):

```cpp
    if (result != NULL) {
        is_loopback = true;
    }
    return is_loopback;   // was: return true;
}
```

Recommended follow-up (separate): the IPv6 `daddr` lookup must use
`LOOP_BACK_IPV6_MAP`, not `LOOP_BACK_IPV4_MAP`.
