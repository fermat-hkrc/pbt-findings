## Summary

`GridItemDragManager::FindAvailableColumn(matrix, row, colSpan, crossCount)` returns the first free column for an item of width `colSpan` within a grid of `crossCount` columns. When the target `row` is absent from the matrix, the function immediately returns `0` — before checking whether `colSpan > crossCount`. This allows an item wider than the entire grid to be assigned column 0, violating the documented contract that the function must return `-1` when no space is available.

## Contract

From `frameworks/core/components_ng/pattern/grid/grid_item_drag_manager.h:345-351`:

```cpp
/**
 * @brief Finds the first available column in a row that can fit the given column span.
 * @param matrix The simulated grid matrix.
 * @param row The row to search.
 * @param colSpan The required column span.
 * @param crossCount The total number of columns.
 * @return The starting column index, or -1 if no space is available.
 */
int32_t FindAvailableColumn(const SimMatrix& matrix, int32_t row,
    int32_t colSpan, int32_t crossCount) const;
```

Required behavior:
- return the starting column index when `colSpan` fits in the row
- return `-1` when no space is available — including the impossible-span case `colSpan > crossCount`

## Existing Oracle in Unit Tests

`test/unittest/core/pattern/grid/grid_item_drag_manager_test.cpp:338`:

```cpp
GridItemDragManager::SimMatrix matrix;
matrix[0] = {};                            // row exists, is empty
int32_t col = manager->FindAvailableColumn(matrix, 0, 5, 4);  // colSpan=5 > crossCount=4
EXPECT_EQ(col, -1);
```

The oracle confirms `-1` when `colSpan` exceeds `crossCount` — even on an empty row. The bug occurs only when the row is **absent** (not even an empty entry): the absent-row early return fires before the span check, so this oracle never exercises the failing path.

## Vulnerable Code

`frameworks/core/components_ng/pattern/grid/grid_item_drag_manager.cpp:1247-1267`:

```cpp
int32_t GridItemDragManager::FindAvailableColumn(
    const SimMatrix& matrix, int32_t row, int32_t colSpan, int32_t crossCount) const
{
    auto it = matrix.find(row);
    if (it == matrix.end()) {
        return 0;                                          // BUG: skips all guards
    }
    if (static_cast<int32_t>(it->second.size()) + colSpan > crossCount) {
        return -1;                                         // never reached for absent row
    }
    // ... linear scan
```

## Root Cause

The intent of the early return is: an absent row means all columns are free, so the item fits at column 0. That invariant holds **only if** `colSpan <= crossCount`. The very next line guards exactly the invalid case, but the early return bypasses it entirely. The result is that an impossible-span item (`colSpan > crossCount`) placed into an unallocated row is reported as fitting at column 0 instead of being rejected with `-1`.

## When the Bug Triggers

Any call where:
- `row` is not a key in `matrix`, AND
- `colSpan > crossCount`

This can occur during drag-and-drop reorder when the drag target is being placed into a row that has not yet been allocated in `simMatrix_` (e.g. dragging an item to a new row at the bottom of the grid) and the dragged item's `colSpan` exceeds the grid width.

## Minimal Counterexample

```cpp
GridItemDragManager::SimMatrix empty;
// row 0 is not in the matrix
int32_t result = manager->FindAvailableColumn(empty, 0, 5, 4);
// Expected: -1   (span 5 cannot fit in a 4-column grid)
// Actual:    0   (early return before the span check)
```

## Why Existing Tests Missed It

The existing oracle at `grid_item_drag_manager_test.cpp:338` covers the impossible-span case, but only for a row that **exists** in the matrix (as an empty entry). The absent-row path — the only path that hits the buggy early return — was never exercised by example-based tests.

## How PBT Detected It

The PBT suite in `test/unittest/core/pattern/grid/find_available_column_pbt_test.cpp` encoded the contract directly across several properties:

| Property | Test | Result |
|---|---|---|
| Impossible span → -1 | `ImpossibleSpan_ReturnsMinus1` | FAIL |
| Valid result in bounds | `ValidResult_InBounds` | PASS |
| Valid result covers free cells | `ValidResult_CoversFreeRange` | PASS |
| Valid result is leftmost | `ValidResult_IsLeftmost` | PASS |
| Full row → -1 | `FullRow_ReturnsMinus1` | PASS |
| Minimal counterexample | `MinimalCounterexample_EmptyMatrixSpanExceedsGrid` | FAIL |

Boundary-biased generation produced `crossCount = 1..8` and `colSpan = crossCount+1 .. crossCount+4`, and the absent-row path was hit on roughly half of all iterations, so the failure reproduced reliably.

## Impact

- Silent wrong result: the caller receives a plausible-looking column index (`0`) for an item that cannot physically fit.
- Downstream drag-and-drop placement may proceed against an invalid column, leading to incorrect grid layout rather than a guarded rejection.
- No crash; the bug manifests as wrong layout state.

## Suggested Fix

Move the impossibility guard ahead of the row lookup so it applies to both the present-row and absent-row paths:

```cpp
int32_t GridItemDragManager::FindAvailableColumn(
    const SimMatrix& matrix, int32_t row, int32_t colSpan, int32_t crossCount) const
{
    if (colSpan <= 0 || colSpan > crossCount) {   // guard first
        return -1;
    }
    auto it = matrix.find(row);
    if (it == matrix.end()) {
        return 0;   // absent row is all-free; span fits since colSpan <= crossCount
    }
    // ... rest unchanged
```
