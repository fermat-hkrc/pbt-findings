## Summary

`Color::LineColorTransition` interpolates two colors by casting the **channel
delta alone** to `uint8_t` before adding the start channel:

```cpp
red = static_cast<uint8_t>((endColor.GetRed() - startColor.GetRed()) * percent)
    + startColor.GetRed();
```

When any RGB channel decreases (`end < start`), the delta is negative, so
`static_cast<uint8_t>(negative_float)` is **undefined behavior**. On ARM the
hardware saturates to 0 and the channel never transitions (flat gradient); on
x86 it wraps mod 256 and produces an off-by-one / off-by-two hue.

The bug is reachable from the **legacy JS-UI** DataPanel gradient path
(`rosen_render_data_panel.cpp`, 6 call sites). Modern ArkTS/ETS apps route
`DataPanel` through `components_ng/pattern/data_panel/`, which uses the
Skia/Drawing gradient API and does **not** call `LineColorTransition`.

Confirmed and fixed under internal ticket `DTS2026070856858`.

## Vulnerable Code

`frameworks/core/components/common/properties/color.cpp:375` — one line per
channel, same pattern:

```cpp
red = static_cast<uint8_t>((endColor.GetRed() - startColor.GetRed()) * percent)
    + startColor.GetRed();
//    ^^^^^^^^^^^^^^^^^^^^^ cast here ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//    Problem: (end - start) * percent can be NEGATIVE
//    Casting a negative float to uint8_t is undefined behavior
```

Execution trace for `start.red=255, end.red=0, percent=0.5`:

```
Step 1: (end - start)           → (0 - 255) = -255        (int, promoted from uint8_t)
Step 2: delta * percent         → -255 * 0.5 = -127.5     (double)
Step 3: static_cast<uint8_t>()  → uint8_t(-127.5) = ???   ← UNDEFINED BEHAVIOR
Step 4: ??? + start.red         → garbage + 255 = wrong
```

C++ promotes both `uint8_t` operands to `int` before the subtraction, so the
delta is a true negative `int` — not a modular wrap at the `uint8_t` level.
The cast then applies to a negative `double`.

The correct form moves the cast after the full interpolation:

```cpp
red = static_cast<uint8_t>(
    startColor.GetRed() + (endColor.GetRed() - startColor.GetRed()) * percent);
//  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//  always in [0, 255] for percent ∈ [0,1] → cast is safe
```

## Trigger Conditions

1. A legacy JS-UI (HML) app uses `<data-panel>` with a gradient whose start and
   end colors have at least one RGB channel decreasing (e.g. red→blue:
   red 255→0).
2. `rosen_render_data_panel.cpp` calls
   `Color::LineColorTransition(end, start, percent)` (or the reverse) with
   `percent ∈ (0, 1)`.
3. For each decreasing channel, the early `static_cast<uint8_t>` of a negative
   float is UB:
   - **ARM:** `fcvtzu` saturates to 0 → channel stays flat at start.
   - **x86/emulator:** wraps mod 256 → off-by-one / off-by-two hue.

**Not reachable from modern ArkTS/ETS apps** — the `_ng` DataPanel does not call
this function. Callers never pass `percent > 1`; the defect is specifically the
decreasing-channel case.

## Impact

- **Visual corruption of legacy DataPanel gradients** whenever any channel
  decreases between the gradient endpoints (the common case for contrasting
  colors).
- Not a crash; the wrong color is subtle (off-hue gradient band) and hard to
  spot by eye in multi-arc circular data panels.
- **Medium:** real UB on a live production path, but scoped to the legacy
  JS-UI `RenderDataPanel` pipeline only. Modern ArkTS apps are unaffected.

## Minimal Counterexample

Pinned PBT witness:

```
start = ARGB(0xFF, 10, 0, 0)
end   = ARGB(0xFF,  5, 0, 0)
p     = 0.5
// correct: trunc(10 + (5-10)*0.5) = trunc(7.5) = 7
// SUT (x86 wrap): returns 8
```

Any red→blue / white→black / other decreasing-channel pair also triggers.

## How PBT Detected This

`line_color_transition_pbt_test` / `LineColorTransitionBugDocs.*` — properties
that assert channel-wise linear interpolation for arbitrary start/end colors
(including decreasing channels). The only in-tree unit test
(`test/unittest/interfaces/ace_kit/color_test.cpp:154`) only exercises
**increasing** channels (black→white), so the decreasing path was never covered.

## Suggested Fix

Move the cast after the full float computation (one line per channel):

```cpp
red   = static_cast<uint8_t>(startColor.GetRed()
        + (endColor.GetRed()   - startColor.GetRed())   * percent);
green = static_cast<uint8_t>(startColor.GetGreen()
        + (endColor.GetGreen() - startColor.GetGreen()) * percent);
blue  = static_cast<uint8_t>(startColor.GetBlue()
        + (endColor.GetBlue()  - startColor.GetBlue())  * percent);
```

Root cause is casting too early — before adding `start`, which would have
brought the value back into `[0, 255]`.
