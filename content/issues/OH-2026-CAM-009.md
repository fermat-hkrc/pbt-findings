## Summary

Two copy-pasted sites parse `OHOS_ABILITY_MOON_CAPTURE_BOOST` as
`[mode][minRatio][maxRatio][fovMin,fovMax,fovRef]*`. After the three header
words, both read `ui32[i+1]` / `[i+2]` and do `i += 2` with only
`i < item.count` on the outer loop → heap **OOB** on a truncated FOV tail.

Same sketch file already bounds the float sibling
(`UpdateSpecSketchReferenceFovRatio`: `while (i < count - REFERENCE_VALUE_OFFSET)`).
Not High: well-formed tables OK. One root, two sites — not two tickets.

Confirmed and fixed by developers (`DTS2026080813794`).

## Vulnerable Code

| Site | File | Function |
|------|------|----------|
| A | `sketch_wrapper.cpp` | `SketchWrapper::UpdateSketchConfigFromMoonCaptureBoostConfig` (~451–496) |
| B | `moon_capture_boost_feature.cpp` | `MoonCaptureBoostFeature` ctor / FOV parse (~30–77) |

```cpp
// both sites, identical FOV body
fovRange.zoomMin = static_cast<float>(item.data.ui32[i]) / SKETCH_DIV;
fovRange.zoomMax = static_cast<float>(item.data.ui32[i + 1]) / SKETCH_DIV;        // unbound
fovRange.referenceValue = static_cast<float>(item.data.ui32[i + 2]) / SKETCH_DIV; // unbound
i = i + 2;  // for-loop also i++ → net +3
```

Safe contrast — same sketch file, different ability:

```cpp
while (i < count - REFERENCE_VALUE_OFFSET) {  // room for [i],[i+1],[i+2]
    SketchReferenceFovRange fovRange = { data[i], data[i+1], data[i+2] };
    i = i + FOV_DATA_LENGTH;
}
```

Root cause: stride-3 FOV look-ahead copied twice; neither bounds remaining
length.

## Trigger Conditions

1. HAL `OHOS_ABILITY_MOON_CAPTURE_BOOST` is truncated mid-FOV (1–2 leftover
   words after headers, e.g. count 4 or 5).
2. Sketch config update or `MoonCaptureBoostFeature` construction runs.
3. FOV body executes with `i + 2 >= count`.

## Impact

- Heap OOB read while filling sketch / moon FOV ranges.
- Medium: complete FOV triples unaffected; field hit needs truncated
  mid-triple metadata. FW bound still wrong vs sketch’s own spec-FOV guard.
- One bound pattern covers both sites (prefer shared helper).

## Minimal Counterexample

| blob shape | Result |
|------------|--------|
| `{mode,minR,maxR, fMin,fMax,fRef}` | OK |
| `{mode,minR,maxR, fMin,fMax}` (count=5) | **OOB** on `[i+2]` |
| `{mode,minR,maxR, fMin}` (count=4) | **OOB** on `[i+1]`/`[i+2]` |

## How PBT Detected This

`pbt-native/moon_fov_ui32_triple_{compat.h,real.cpp}` (group tag
`moon_fov_ui32_triple`). Same look-ahead shape also modeled by
`sketch_fov_lookahead_pbt_test`.

| Harness slice | Result |
|---------------|--------|
| room for 3 FOV words | PASS |
| 1–2 words left | **FAIL** / throw |

```bash
cmake -S pbt-native -B pbt-native/build -DCMAKE_BUILD_TYPE=Release
cmake --build pbt-native/build -j --target sketch_fov_lookahead_pbt_test
./pbt-native/build/sketch_fov_lookahead_pbt_test
```

## Suggested Fix

Both sites, immediately before the triple read:

```cpp
if (i + 2 >= item.count) {
    MEDIA_ERR_LOG("moon FOV triple truncated at i=%{public}u count=%{public}u",
        i, item.count);
    break;
}
fovRange.zoomMin = static_cast<float>(item.data.ui32[i]) / SKETCH_DIV;
fovRange.zoomMax = static_cast<float>(item.data.ui32[i + 1]) / SKETCH_DIV;
fovRange.referenceValue = static_cast<float>(item.data.ui32[i + 2]) / SKETCH_DIV;
i = i + 2;
```

After fix: short trailing FOV PASS; full triples stay PASS.
