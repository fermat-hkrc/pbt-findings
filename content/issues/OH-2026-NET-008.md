## Summary

`CommonUtils::StrToUint64` used `strtoull`. POSIX `strtoull("-1")` wraps to
`2^64-1` without setting `ERANGE`, so `StrToUint64("-1", 0)` returned
`UINT64_MAX` instead of `defaultErr`. A leading minus is not a uint64 numeral.

Twin `StrToUint` (uint32) used to reject the same wrap via `result > UINT32_MAX`.
`StrToUint64` had no such ceiling (`result > UINT64_MAX` never fires).

Confirmed and fixed under `DTS2026071727054` (upstream `21584d87f` switched
the helper to `std::from_chars`, which rejects `'-'`).

## Vulnerable Code

Old `StrToUint64` (`netmanager_base_common_utils.cpp`):

```cpp
uint64_t result = std::strtoull(value.c_str(), &pEnd, 0);
if (pEnd == value.c_str() || errno == ERANGE) {
    return defaultErr;
}
return result;
```

Caller: `route_manager.cpp` — `StrToUint64(maskLenStr, UINT64_MAX)`.

## Trigger Conditions

Input is a decimal string with a leading minus (`"-1"`,
`"-9223372036854775808"`). `errno` is not `ERANGE`; the wrap looks in-range.

## Impact

`"-1"` is indistinguishable from a successful `UINT64_MAX`. Medium — silent
wrong unsigned value, not a crash. Official unit test only covered `""` and
`"100"`.

## Minimal Counterexample

```
StrToUint64("-1", 0)                       // 18446744073709551615; expected 0
StrToUint64("-9223372036854775808", 0)     // 2^63; expected 0
```

## How PBT Detected This

`pbt-native/str_to_uint64_pbt_test.cpp`

Law: `∀ n < 0. StrToUint64(to_string(n), d) = d`

Witness `"-1"`.

## Suggested Fix

Shipped as `from_chars` (`21584d87f`):

```cpp
uint64_t result = 0;
auto [ptr, ec] = std::from_chars(value.data(), value.data() + value.size(), result);
if (ec != std::errc{} || ptr != value.data() + value.size()) {
    return defaultErr;
}
return result;
```

`from_chars` on `uint64_t` does not accept `'-'`. Twin `StrToUint` is the same
pattern. Stronger than a leading-minus guard; no `> UINT64_MAX`.
