## Summary

`PasteboardService::ProcessDistributedDelayUri` converts a local file URI to a
DFS/distributed URI and encodes it for the remote peer. It calls
`PasteboardWebController::CheckAppUriPermission(data)`, which writes the per-record
`HasGrantUriPermission` flag — but then **never reads that flag** before exporting.
A URI record that failed (or never received) grant is still rewritten to distributed
form and sent on the delay path. The sibling full-data path `GenerateDistributedUri`
already refuses non-owned, ungranted URIs before DFS conversion; the delay-URI path
has no equivalent branch, so the permission gate is **fail-open**.

This is a logic / access-control omission, **not a crash** — the path still returns
`E_OK` and encodes a well-formed TLV. Failure mode is export of a URI that should
have been refused.

Confirmed and fixed under `DTS2026071412383`. Fix merged in
[MR !2062](https://gitcode.com/openharmony/distributeddatamgr_pasteboard/merge_requests/2062)
(`4b667079` / commit `70bb3843`, issue [#1658](https://gitcode.com/openharmony/distributeddatamgr_pasteboard/issues/1658)).

## Vulnerable Code

`services/core/src/pasteboard_service.cpp` (~4297–4345) — caller then the export:

```cpp
// GetDistributedDelayEntry — validates recordId, loads entry, then:
if (mimeType == MIMETYPE_TEXT_URI) {
    ret = ProcessDistributedDelayUri(evt.user, *data, entry, rawData);
}

// ProcessDistributedDelayUri:
auto uri = entry.ConvertToUri();
{
    std::unique_lock<std::shared_mutex> write(pasteDataMutex_);
    PasteboardWebController::GetInstance().CheckAppUriPermission(data);
    // BUG: never reads HasGrantUriPermission (and/or own-URI) for this record
}
// always: GetDfsUrisDirFromLocal → SetValue(distributedUri) → Encode
```

The grant predicate exists and is consulted in two sibling sites in the same file:
`GenerateDistributedUri` (~4705) and `CheckUriPermission` (~2220). The delay-URI
path is the **only** `CheckAppUriPermission` caller that writes the flag then skips
a sensitive action (DFS export) without reading it.

```cpp
// GenerateDistributedUri (sibling — correct):
if (!IsBundleOwnUriPermission(bundleName, *uri) && !hasGrantUriPermission) {
    continue; // skip DFS conversion
}
```

## When the Bug Triggers

The defect is live on a narrow scenario — delay record + URI mime + distributed
peer fetch of that entry + grant false:

1. Remote/distributed peer requests a delayed entry of type URI.
2. `GetDistributedDelayEntry` loads the local entry value, then `ProcessDistributedDelayUri`.
3. `CheckAppUriPermission` sets grant flags on records (via `GetOriginUri()` / token of the paste).
4. The local file path is **always** rewritten to a DFS URI and encoded into the TLV returned to the peer — even when the flag is false.

Edge case that does not change the missing-branch fact: if the delayed URI was not
yet attached on the record (`GetLocalEntryValue` capacity skip), `GetOriginUri()` may
be empty → the check may not set a flag → grant stays default `false` → the unguarded
export still proceeds.

## Minimal Counterexample

| `HasGrantUriPermission` (after `CheckAppUriPermission`) | Production | Correct (consult flag) |
|---|---|---|
| true | ALLOW | ALLOW |
| **false** | **ALLOW (bug)** | **deny — no URI export** |

```cpp
PasteData data;               // contains a URI record whose grant flag is false
PasteDataEntry entry = ...;   // mimeType == MIMETYPE_TEXT_URI
// ProcessDistributedDelayUri(userId, data, entry, rawData)
//   CheckAppUriPermission(data)  → writes HasGrantUriPermission = false
//   (no read of the flag)
//   GetDfsUrisDirFromLocal → encode → return E_OK   ← exported despite no grant
```

## How PBT Detected This

A RapidCheck differential model (`distributed_delay_uri_perm_pbt_test`) compared the
production permission decision against a correct gate and against the sibling
include rule. The production gate body has **no branch** on grant — that absence is
what the failing properties hit. RapidCheck shrank the witness to `hasGrant=false`,
production `ALLOW` vs correct `NO_URI_PERM`.

| Property | Result |
|---|---|
| `GrantedRecordAllowed` | PASS |
| `WithoutGrantMustDeny` | **FAIL** |
| `ProductionMatchesCorrectForAllFlags` | **FAIL** |
| `SiblingGenerateDistributedUriRequiresOwnOrGrant` | PASS (sibling model) |
| `DelayNotLooserThanSiblingWhenNeitherOwnNorGrant` | **FAIL** |

A repo-wide pattern audit confirmed the write-then-ignore-before-export pattern is
**unique** to `ProcessDistributedDelayUri` — every other `CheckAppUriPermission` call
site either consults the flag before its sensitive action (`ProcessDelayHtmlEntry`,
`SetCurrentData`, `GetDistributedDelayData`) or stores it for a later path that does.
So this is one missed branch, not a systemic ignore-grant design.

## Impact

- **Security:** a URI record that failed (or never received) grant may be rewritten to distributed form and sent over the distributed clip channel. The receiver trusts the exported DFS URI (`ProcessRemoteDelayUri` sets grant true on the remote side), so the omission propagates.
- Inconsistent with the same-file sibling `GenerateDistributedUri` and with `CheckUriPermission`.
- **Medium:** scoped to distributed **delay URI** mime (needs delay + distributed + URI); HTML/plain entry paths differ. Peer is the distributed clip channel, not a local unprivileged same-device read.

Why not Low: real distributed path, access-control omission (flags set, never
consulted), PBT differential fails on a shrunk witness. Why not Critical: scoped to
the delay-URI mime rather than a full paste rewrite.

## Suggested Fix

Thread the `recordId` (already validated by `GetDistributedDelayEntry`) into
`ProcessDistributedDelayUri` and consult the flag just written by
`CheckAppUriPermission` before DFS export — matching the gate the sibling
`GenerateDistributedUri` already enforces.

```diff
### services/core/include/pasteboard_service.h
     int32_t ProcessDistributedDelayUri(int32_t userId, PasteData &data, PasteDataEntry &entry,
-        std::vector<uint8_t> &rawData);
+        uint32_t recordId, std::vector<uint8_t> &rawData);

### services/core/src/pasteboard_service.cpp
     std::string mimeType = entry.GetMimeType();
     if (mimeType == MIMETYPE_TEXT_URI) {
-        ret = ProcessDistributedDelayUri(evt.user, *data, entry, rawData);
+        ret = ProcessDistributedDelayUri(evt.user, *data, entry, recordId, rawData);
     }
@@ int32_t PasteboardService::ProcessDistributedDelayUri(int32_t userId, PasteData &data, PasteDataEntry &entry,
-    std::vector<uint8_t> &rawData)
+    uint32_t recordId, std::vector<uint8_t> &rawData)
 {
     ...
     {
         std::unique_lock<std::shared_mutex> write(pasteDataMutex_);
         PasteboardWebController::GetInstance().CheckAppUriPermission(data);
+        auto item = data.GetRecordById(recordId);
+        PASTEBOARD_CHECK_AND_RETURN_RET_LOGE(item != nullptr,
+            static_cast<int32_t>(PasteboardError::INVALID_RECORD_ID),
+            PASTEBOARD_MODULE_SERVICE, "record[%{public}u] invalid", recordId);
+        PASTEBOARD_CHECK_AND_RETURN_RET_LOGE(item->HasGrantUriPermission(),
+            static_cast<int32_t>(PasteboardError::INVALID_URI_ERROR),
+            PASTEBOARD_MODULE_SERVICE, "no permission, uri=%{private}s", uri->ToString().c_str());
     }
```

A `try/catch`-style fix is irrelevant here (no exception). Reordering the check
later doesn't help — the bug is a missing read of an already-computed result, so the
minimal fix is to read it. The grant-only gate is stricter than the sibling for the
owned-without-grant case (sibling accepts `owned || grant`); matching the sibling
exactly is an optional variation that replaces the grant check with
`IsBundleOwnUriPermission(...) || item->HasGrantUriPermission()`.
