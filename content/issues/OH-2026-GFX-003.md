## Summary

`OHOS::Rosen::Drawing::RectF::Round()` converted each edge with
`DrawingFloatSaturate2Int(x + 0.5f)` (truncate toward zero after adding half).
That is nearest-integer only for **non-negative** values. For negative half-values
(e.g. `-0.5`) it produces `0` instead of `std::round(-0.5) == -1`, so any rect
with a negative edge is rounded away from the mathematical nearest integer.

Confirmed and fixed upstream under `DTS2026062516469`. Merged PR
[#30954](https://gitcode.com/openharmony/graphic_graphic_2d/pull/30954)
(`669fd6b0bf`, 2026-06-27) replaces the `x + 0.5f` form with `std::round(x)`.

## Vulnerable Code

`rosen/modules/2d_graphics/include/utils/rect.h` — pre-fix:

```cpp
inline void RectF::Round()
{
    left_   = DrawingFloatSaturate2Int(left_   + 0.5f);
    right_  = DrawingFloatSaturate2Int(right_  + 0.5f);
    top_    = DrawingFloatSaturate2Int(top_    + 0.5f);
    bottom_ = DrawingFloatSaturate2Int(bottom_ + 0.5f);
}
```

`DrawingFloatSaturate2Int` truncates toward zero. Adding `0.5f` then truncating
is the classic “round half up toward +∞ for positives” idiom; for negatives,
`-0.5 + 0.5 = 0` truncates to `0`, while nearest-int / banker's
`std::round(-0.5)` is `-1`.

## Trigger Conditions

1. A drawing/layout path constructs a `RectF` with at least one edge that is a
   negative half-value (or more generally a negative float whose nearest int
   differs from truncate-toward-zero of `x + 0.5`).
2. Something calls `RectF::Round()` (pixel snapping / integer rect conversion).
3. That edge is stored as the wrong integer (e.g. `-0.5` → `0` instead of `-1`),
   shifting the rounded rect by one pixel on that edge.

## Impact

- **Incorrect pixel-snapped geometry** for any rect that extends into negative
  coordinates (offscreen, transformed, or parent-relative layouts that produce
  negative edges).
- Not a crash; silent one-pixel (or larger) mis-rounding on the negative side.
- **Medium:** real algebraic defect on a public geometry helper; impact is
  visual/layout correctness rather than process death or security.

## Minimal Counterexample

| Edge value | Pre-fix (`x+0.5` truncate) | Correct (`std::round`) |
|---|---|---|
| `-0.5` | `0` ❌ | `-1` |
| `0.5` | `1` ✅ | `1` |
| `-1.5` | `-1` ❌ | `-2` |

Detected by RapidCheck property `RectFPBT.RoundMatchesStdRound` (algebraic
invariant: `Round()` must match `std::round` per edge). Minimal witness:
`right = -0.5` → actual `0`, expected `-1`.

## How PBT Detected This

`pbt-native/rect_f_pbt_test.cpp` — property `RectFPBT.RoundMatchesStdRound`
asserts edge-wise equivalence of `RectF::Round()` to `std::round`. The first
failing inputs were negative half-values; RapidCheck shrunk to `right = -0.5`.

## Suggested Fix

(Merged in PR #30954 — matches the original report line-for-line.)

```cpp
inline void RectF::Round()
{
    left_   = DrawingFloatSaturate2Int(std::round(left_));
    right_  = DrawingFloatSaturate2Int(std::round(right_));
    top_    = DrawingFloatSaturate2Int(std::round(top_));
    bottom_ = DrawingFloatSaturate2Int(std::round(bottom_));
}
```

Unit tests added: `RectFRound001` / `002` / `003` in
`rosen/test/2d_graphics/unittest/utils/rect_test.cpp` (positive / negative /
mixed).
