## Summary

In `SpanString::DecodeTlvExt`, the `TLV_CUSTOM_MARSHALL_BUFFER_START` case
extracts the ExtSpan user-data payload for the `unmarshallCallback` with

```cpp
auto endOfUserDataArrBuff = buffLength + cursor + cursor - lastCursor;
std::vector<uint8_t> bufferSubVec(buff.begin() + cursor, buff.begin() + endOfUserDataArrBuff);
```

At that point `cursor == lastCursor + 8` (two `ReadInt32` for `start` and
`length`), so `endOfUserDataArrBuff == lastCursor + buffLength + 16` —
**16 bytes past the section end**. The loop itself advances with
`cursor = lastCursor + buffLength`, confirming the section ends at
`lastCursor + buffLength`; the `+ cursor - lastCursor` term double-counts the
section header.

The `std::vector` range constructor therefore reads past the custom-marshall
section. When the section is the last one in `buff`, the end iterator is past
`buff.end()` — iterator UB / crash. Mid-buffer, it silently copies the next
section's 16 header bytes into the ExtSpan user data handed to
`unmarshallCallback`.

Confirmed under `DTS2026092958405`; not yet fixed.

## Vulnerable Code

`frameworks/core/components_ng/pattern/text/span/span_string.cpp`
(`SpanString::DecodeTlvExt`):

```cpp
case TLV_CUSTOM_MARSHALL_BUFFER_START: {
    CHECK_NULL_BREAK(unmarshallCallback);
    auto start = TLVUtil::ReadInt32(buff, cursor);
    auto length = TLVUtil::ReadInt32(buff, cursor);
    auto endOfUserDataArrBuff = buffLength + cursor + cursor - lastCursor;  // lastCursor + buffLength + 16
    std::vector<uint8_t> bufferSubVec(buff.begin() + cursor, buff.begin() + endOfUserDataArrBuff);
    ...
    cursor = lastCursor + buffLength;   // section end per the loop's own arithmetic
    break;
}
```

## Trigger Conditions

Decoding (`DecodeTlv`/`DecodeTlvExt`) a TLV buffer containing a
`TLV_CUSTOM_MARSHALL_BUFFER_START` section — i.e. a styled string carrying a
custom `ExtSpan` (custom-span marshall via `unmarshallCallback`). The
over-read is largest-reachable when the section sits at the end of the
buffer.

## Impact

Medium — out-of-bounds read of up to 16 bytes: crash (UB) when the section is
last, or 16 bytes of adjacent TLV header leaking into the decoded ExtSpan
payload (silent data corruption).

## Minimal Counterexample

Encode a styled string whose last section is a custom-marshall buffer of
payload length `L`; decode it:

```
section layout: [tag][buffLength=12+L][start=4][length=4][user data L]
lastCursor (after tag+len reads) = T+5; cursor after start/length = T+13
end computed  = buffLength + 2*cursor - lastCursor = T+buffLength+21
section end   = lastCursor + buffLength            = T+buffLength+5
over-read     = 16 bytes past the section (and past buff.end() if last)
```

## How PBT Detected This

Custom-marshall round-trip property — `decode(encode(x)) == x` with an
`ExtSpan`-carrying styled string: the decoded ExtSpan payload equals the
encoded user data only when the section is followed by ≥16 more bytes;
shrunk witnesses put the custom section last, turning the mismatch into an
over-end iterator.

## Suggested Fix

End the sub-vector at the section end:

```diff
-    auto endOfUserDataArrBuff = buffLength + cursor + cursor - lastCursor;
+    auto endOfUserDataArrBuff = lastCursor + buffLength;
```

User data then spans `[cursor, lastCursor + buffLength)` — exactly the bytes
the loop skips with `cursor = lastCursor + buffLength`.
