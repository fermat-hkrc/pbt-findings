## Summary

`ark::verifier::NumToStr(Int val, ...)` negates negative inputs before digit extraction. For the minimum signed integer (`INT_MIN` / `INT32_MIN`), the positive magnitude cannot be represented in the same signed type, so `val = -val` is signed-overflow undefined behaviour. On the current toolchain this produces garbage diagnostic text instead of the expected decimal representation.

No in-tree caller was found to pass `INT_MIN` at the time of discovery; existing callers pass non-negative values or exclude the minimum sentinel before calling. The impact is a latent/future hardening risk and a sanitizer failure.

## Contract

`static_core/verification/util/str.h:39-40`:

```cpp
template <typename Int, typename = std::enable_if_t<std::is_integral_v<Int>>>
PandaString NumToStr(Int val, Int base = 10, size_t width = 0)
```

`static_core/verification/util/str.h:43-47`:

```cpp
if (val < 0) {
    neg = true;
    val = -val;
}
```

Formatting an integral value should produce the corresponding textual representation. For base-10 signed integers, `NumToStr(n)` must match `std::to_string(n)`, including the minimum representable value.

## Vulnerable Code

`static_core/verification/util/str.h`, lines 43–47:

```cpp
if (val < 0) {
    neg = true;
    val = -val;   // BUG: signed overflow when val == INT_MIN
}
```

`-INT_MIN` cannot be represented in a signed `int` on two's-complement machines. C++ signed overflow is undefined behaviour; UBSan reports it at runtime.

## Root Cause

The digit-extraction loop operates on a signed type. To handle negative values the code negates `val` into the same signed type, which overflows for the minimum representable value. The overflow is not caught by the existing test suite because the only negative-value test uses `-1456`, an ordinary value whose positive magnitude is representable.

## Minimal Counterexample

```cpp
int32_t n = std::numeric_limits<int32_t>::min();
auto got = ark::verifier::NumToStr(n);
```

Expected:

```
-2147483648
```

Actual on the current toolchain:

```
-./,),(-*,(
```

UBSan output:

```
runtime error: negation of -2147483648 cannot be represented in type 'int';
cast to an unsigned type to negate this value to itself
```

## When the Bug Triggers

### Non-triggering: ordinary negative values

```cpp
NumToStr(-1456) == "-1456"  // passes — 1456 is representable
```

### Trigger: minimum signed value

```cpp
NumToStr(std::numeric_limits<int32_t>::min())  // UB — positive magnitude overflows
```

## Why Existing Tests Missed It

`static_core/verification/util/tests/str_test.cpp:47` tests `NumToStr(-1456_I) == "-1456"`, proving negative formatting is intended, but it only covers an ordinary value. No test covers the signed minimum where negation overflows.

## How PBT Detected This

A RapidCheck differential property compared `NumToStr` output against `std::to_string` for random `int32_t` inputs. The triage property excluded the exact failing value:

```cpp
RC_PRE(val != std::numeric_limits<int32_t>::min());
// INT32_MIN: -val overflows inside NumToStr; exclude it.
```

A dedicated `BugDocs` test removes that exclusion and pins `INT_MIN` as required behaviour, confirming the failure:

```
[ RUN      ] StrPbt_BugDocs.NumToStrHandlesIntMin
Expected equality of these values:
  std::string(got)    Which is: "-./,),(-*,("
  std::to_string(n)   Which is: "-2147483648"
[  FAILED  ] StrPbt_BugDocs.NumToStrHandlesIntMin
```

## Suggested Fix

Compute the magnitude in an unsigned type to avoid signed overflow entirely:

```cpp
using UInt = std::make_unsigned_t<Int>;
const bool neg = val < 0;
UInt uval = neg ? static_cast<UInt>(-(val + 1)) + 1 : static_cast<UInt>(val);
const auto ubase = static_cast<UInt>(base);

do {
    char c = static_cast<char>(uval % ubase);
    constexpr char LETTER_DIGIT_START = static_cast<char>(10);
    if (c >= LETTER_DIGIT_START) {
        c += 'a' - LETTER_DIGIT_START;
    } else {
        c += '0';
    }
    result.insert(0, 1, c);
    uval /= ubase;
} while (uval);
```

The key change is replacing `val % base` / `val = val / base` with `uval % ubase` / `uval /= ubase` so the digit loop runs on an unsigned type throughout.

## Impact

The overflow produces garbage verifier diagnostic text but does not affect verifier accept/reject decisions; no in-tree caller was found to pass `INT_MIN` at the time of discovery. The primary risk is a UBSan failure and a latent correctness hazard if future callers extend coverage to the full signed integer range.
