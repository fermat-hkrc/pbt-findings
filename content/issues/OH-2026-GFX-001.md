## Summary

`Point3::operator+` adds the wrong operands for the X and Y components. The X component is computed as `p1.x_ + p1.y_` (ignoring `p2.x_`), and the Y component as `p2.x_ + p2.y_` (ignoring `p1.y_`). Only the Z component is correct. As a result vector addition is not commutative (`a + b != b + a`), violating the fundamental algebraic law of vector addition.

## Contract

Vector addition must be componentwise: `Point3(p1.x_ + p2.x_, p1.y_ + p2.y_, p1.z_ + p2.z_)`, and it must be commutative: `a + b == b + a`.

This contract is encoded by every other vector `operator+`/`operator-` in the same codebase:
- `PointF::operator+` at `point.h:173` correctly uses `p1.x_ + p2.x_`
- `Point3::operator-` correctly uses `p1.x_ - p2.x_`

`Point3::operator+` alone deviates — strong evidence of a typo rather than an intentional design choice.

## Vulnerable Code

`rosen/modules/2d_graphics/include/utils/point3.h`, `operator+`:

```cpp
inline const Point3 operator+(const Point3& p1, const Point3& p2)
{
    return Point3(p1.x_ + p1.y_, p2.x_ + p2.y_, p1.z_ + p2.z_);
    //              ^^^^^^^^^^^^^^    ^^^^^^^^^^^^^^
    //              BUG: should be p1.x_ + p2.x_   and   p1.y_ + p2.y_
}
```

| Component | Current (buggy) | Correct |
|-----------|-----------------|---------|
| X | `p1.x_ + p1.y_` | `p1.x_ + p2.x_` |
| Y | `p2.x_ + p2.y_` | `p1.y_ + p2.y_` |
| Z | `p1.z_ + p2.z_` (correct) | `p1.z_ + p2.z_` |

## Root Cause

The X expression mixes `p1.x_` with `p1.y_` and ignores `p2.x_`; the Y expression mixes `p2.x_` with `p2.y_` and ignores `p1.y_`. Both operands within each component come from the same point instead of from matching components across the two points.

## Minimal Counterexample

```cpp
#include "utils/point3.h"
using namespace OHOS::Rosen::Drawing;

int main() {
    Point3 a(1.0f, 2.0f, 3.0f);
    Point3 b(4.0f, 5.0f, 6.0f);

    Point3 sum = a + b;
    // Expected: (5.0, 7.0, 9.0)
    // Actual:   (3.0, 9.0, 9.0)  — X is a.x+a.y, Y is b.x+b.y

    assert(sum.GetX() == 5.0f);  // FAILS: got 3.0
    assert(sum.GetY() == 7.0f);  // FAILS: got 9.0
    assert(sum.GetZ() == 9.0f);  // PASS
}
```

## When the Bug Triggers

Any `Point3::operator+` where the operands are not both zero. The result is silently wrong and non-commutative: `a + b != b + a` whenever any component differs between `a` and `b`.

## Why Existing Tests Missed It

No example-based test encoded the commutativity law (`a + b == b + a`) or cross-checked `operator+` against a known componentwise sum with non-zero, non-equal operands. The typo survives any test that only checks symmetric or zero-heavy inputs.

## How PBT Detected It

Property: `Point3PBT.AdditionIsCommutative` — addition of two `Point3` values must be commutative componentwise:

```cpp
RC_ASSERT((a + b) == (b + a));
```

RapidCheck shrank to a minimal witness:

```
a = Point3(0.0, 0.0, 0.0)
b = Point3(4.65661e-08, 0.0, 0.0)   // F(1) ≈ 4.65661e-08

a + b = Point3(0.0, 4.65661e-08, 0.0)
b + a = Point3(0.0, 0.0, 0.0)

(a+b).GetX() == (b+a).GetX()  →  0 == 4.65661e-08  →  FALSE
```

Falsifiable after 5 tests and 4 shrinks. Reproduce the exact run with:

```bash
RC_PARAMS="reproduce=B8BUvlmb0NDUCR1LBRGZpRXav5WSzN0bt1Wd0FGdpZXZQH5rO2CxRQA0R+qjtQcEEAdkv6YLEHBBQH5rO2CxRQAEAUABAAAAEEQAAEA" \
  point3_pbt_test --gtest_filter=Point3PBT.AdditionIsCommutative
```

## Impact

`Point3` is used in 3D camera transforms (`camera3d.h`) and perspective/animation computations. Silent wrong results in vector addition produce visually incorrect 3D effects with no crash or error signal.

## Suggested Fix

```cpp
inline const Point3 operator+(const Point3& p1, const Point3& p2)
{
    return Point3(p1.x_ + p2.x_, p1.y_ + p2.y_, p1.z_ + p2.z_);
}
```

## Verification

Confirmed by:
- the commutativity law (`a + b == b + a`) violated by the implementation
- sibling operators `PointF::operator+` (`point.h:173`) and `Point3::operator-` both using the correct operands
- PBT counterexample shrunken to `a=(0,0,0)`, `b=(4.65661e-08,0,0)`
- upstream fix under internal issue `DTS2026062430430`
