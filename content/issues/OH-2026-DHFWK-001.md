## Summary

`IsUInt8`, `IsUInt16`, and `IsUInt32` validate a `cJSON` number by casting `valueint` to the target unsigned type and then comparing the cast result against `UINT*_MAX`. That check is too late: the narrowing cast has already wrapped the value, so the upper-bound test becomes meaningless for any non-negative input.

As a result, out-of-range JSON numbers are accepted and later silently truncated by callers that cast the same value into the destination type.

## Vulnerable Code

```cpp
bool IsUInt8(const cJSON* jsonObj)
{
    if (jsonObj == NULL || !cJSON_IsNumber(jsonObj)) {
        return false;
    }
    return (jsonObj->valueint >= 0 && static_cast<uint8_t>(jsonObj->valueint) <= UINT8_MAX);
}

bool IsUInt16(const cJSON* jsonObj)
{
    if (jsonObj == NULL || !cJSON_IsNumber(jsonObj)) {
        return false;
    }
    return (jsonObj->valueint >= 0 && static_cast<uint16_t>(jsonObj->valueint) <= UINT16_MAX);
}

bool IsUInt32(const cJSON* jsonObj)
{
    if (jsonObj == NULL || !cJSON_IsNumber(jsonObj)) {
        return false;
    }
    return (jsonObj->valueint >= 0 && static_cast<uint32_t>(jsonObj->valueint) <= UINT32_MAX);
}
```

`static_cast<uintN_t>(valueint) <= UINTN_MAX` is effectively always true once `valueint >= 0`, because the cast truncates the original number before the comparison.

## Trigger Conditions

1. Caller parses a numeric JSON field with `cJSON`
2. Field value is non-negative but exceeds the destination unsigned type
3. `IsUInt8` / `IsUInt16` / `IsUInt32` returns `true` because the casted value still satisfies the bound check
4. Caller performs its own `static_cast<uintN_t>(valueint)`
5. Value wraps and the stored field becomes incorrect

## Impact

- Out-of-range values pass validation
- Downstream callers silently wrap the value during cast
- Device capability / message fields can be corrupted without any error
- The bug is logic corruption, not memory corruption

## Reachable Examples

- `IsUInt8(256)` returns `true` instead of `false`
- `IsUInt16(65536)` returns `true` instead of `false`
- `IsUInt32` has the same structure and should use the same direct comparison pattern

Known affected call sites include capability and parser code that consume these validators and then cast the same value into enums or unsigned integer fields.

## Suggested Fix

Compare the original `valueint` against the limit before any cast:

```cpp
bool IsUInt8(const cJSON* jsonObj)
{
    if (jsonObj == NULL || !cJSON_IsNumber(jsonObj)) {
        return false;
    }
    return (jsonObj->valueint >= 0 && jsonObj->valueint <= UINT8_MAX);
}

bool IsUInt16(const cJSON* jsonObj)
{
    if (jsonObj == NULL || !cJSON_IsNumber(jsonObj)) {
        return false;
    }
    return (jsonObj->valueint >= 0 && jsonObj->valueint <= UINT16_MAX);
}

bool IsUInt32(const cJSON* jsonObj)
{
    if (jsonObj == NULL || !cJSON_IsNumber(jsonObj)) {
        return false;
    }
    return (jsonObj->valueint >= 0 && jsonObj->valueint <= UINT32_MAX);
}
```

## Reproduction

```cpp
cJSON* j = cJSON_CreateNumber(256);
bool ok = IsUInt8(j);
// buggy version: ok == true
// expected: ok == false
```

## PBT Note

The repository already contains regression coverage in `type_validation_pbt_test.cpp` that exercises these validators with generated inputs. This bug is a good example of why PBT helps: the failure is easy to state as a property, but hand-written tests often miss the wraparound boundary unless someone explicitly thinks to try values just past the type limit.
