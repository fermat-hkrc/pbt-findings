## Summary

`napi_type_tag_object` / `napi_check_object_type_tag` pack and unpack a
128-bit tag (`uint64_t lower`, `uint64_t upper`). After tagging an object with
`T`, a check with the same `T` must return true for every legal pair —
including `T.upper == 0` and `{0,0}`.

When `upper == 0`, Ark BigInt drops the zero high limb. The check path
stack-allocates `NapiTypeTag tag;` **uninitialized**, copies one limb into
`lower`, and compares garbage `tag.upper` to `0`. The result is usually
**false** — a correctly tagged object looks untagged. Confirmed and fixed
under `DTS2026082239182`.

## Vulnerable Code

`native_engine/native_api.cpp` `napi_check_object_type_tag` (~4173–4179):

```cpp
size_t size = 2;
NapiTypeTag tag;   // uninitialized
BigIntGetWordsArray(vm, bigintObj, &sign, &size,
                    reinterpret_cast<uint64_t*>(&tag));
if (sign == 0 && ((size == 1) || (size == 2))) {
    *result = (tag.lower == typeTag->lower && tag.upper == typeTag->upper);
}
```

Store always writes two words (`CreateBigWords` size=2). ECMA-262 / Ark BigInt
strips a leading zero limb, so `upper == 0` ⇒ `GetWordsArraySize == 1`. Only
`lower` is written; `tag.upper` is leftover stack. Compare against
`typeTag->upper == 0` fails unless the garbage happens to be 0.

## Contract

- `NapiTypeTag` / Node-API `napi_type_tag`: both fields are unsigned; every
  pair `{lower, upper}` is in range, including `{0,0}` and `{L, 0}`.
- After `napi_type_tag_object(env, obj, &T)`,
  `napi_check_object_type_tag(env, obj, &T, &ok)` must set `ok == true` for
  every `T`, including `T.upper == 0`.
- In-tree sample `TestTypeTagZeroTag` tags and checks `{0,0}` and expects a
  match (`sample/native_module_type_tag_suite/napi_type_tag_suite.cpp`).

## Minimal Counterexample

```cpp
napi_type_tag T = {1, 0};  // or {0, 0}
napi_type_tag_object(env, obj, &T);
bool ok = false;
napi_check_object_type_tag(env, obj, &T, &ok);
// Expected: ok == true
// Actual:   ok == false   (tag.upper is uninitialized)
```

`T = {1, 2}` (nonzero upper) matches. The bug is only the zero-high-half subset.

## How PBT Detected This

Harness: `pbt-native/check_object_type_tag_pbt_test.cpp`. Oracle: tag then
check the same `T`. Storage is poisoned so a missed write of `upper` is
visible.

| Property / regression | Result |
|---|---|
| Round-trip, `upper != 0` | PASS |
| Round-trip, `upper == 0` (incl. `{0,0}`) | FAIL |
| `ZeroUpperTagMustMatch` | FAIL |

## Impact

Functional, not a crash. Addons that use `{L, 0}` or `{0,0}` (sample zero tag,
sequential ids in the low half, etc.) treat a correctly wrapped object as the
wrong C++ type / untagged. `napi_unwrap` / type checks fail. Does **not**
affect tags with `upper != 0` (typical random UUIDs).

## Suggested Fix

Value-initialize so a dropped high limb stays 0:

```cpp
NapiTypeTag tag{};  // was: NapiTypeTag tag;
```
