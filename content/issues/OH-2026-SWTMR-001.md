## Summary

`OsSortLinkGetTargetExpireTime()` in `kernel/base/sched/los_sortlink.c` declares a `UINT64` return type but casts the remaining cycle delta to `UINT32` before returning. This silently truncates the upper 32 bits, causing software timer remaining-time queries to report incorrect (too-small) values for any timer whose remaining interval exceeds `UINT32_MAX` cycles.

## Vulnerable Code

**`kernel/base/sched/los_sortlink.c`**
```c
UINT64 OsSortLinkGetTargetExpireTime(UINT64 currTime, const SortLinkList *targetSortList)
{
    if (currTime >= targetSortList->responseTime) {
        return 0;
    }

    return (UINT32)(targetSortList->responseTime - currTime);  // ← truncates upper 32 bits
}
```

The cast to `UINT32` discards the upper 32 bits of the cycle delta before it is widened back to `UINT64` on return.

## Affected Call Chain

```
timer_gettime()              compat/posix/src/time.c
  └─ OsSwtmrTimeGet()        kernel/base/core/los_swtmr.c
       └─ LOS_SwtmrTimeGet() kernel/base/core/los_swtmr.c
            └─ OsSortLinkGetTargetExpireTime()  ← truncation here
```

Shell output from `kernel/base/misc/swtmr_shellcmd.c` is also affected via `LOS_SwtmrTimeGet()`.

## Evidence

Minimal example:
- `currTime = 0`
- `responseTime = 0x100000000` (`UINT32_MAX + 1 = 4294967296`)

| | Value |
|---|---|
| Expected remaining cycles | `4294967296` |
| Actual return value | `(UINT32)4294967296 == 0` |

## Why This Matters

The truncation threshold in wall time depends on the system clock frequency:

| Clock Frequency | Truncation Threshold |
|---|---|
| 1 GHz | ~4.29 s |
| 500 MHz | ~8.59 s |
| 200 MHz | ~21.47 s |
| 100 MHz | ~42.95 s |

Ordinary multi-second timers on common embedded systems exceed this threshold, making the bug reachable in normal use.

## Scope

- **Confirmed wrong**: remaining-time query path (`timer_gettime()`, `LOS_SwtmrTimeGet()`, shell output)
- **Not claimed**: timer expiry itself firing early or late — not verified from source review

## Impact

- `timer_gettime()` returns incorrect remaining time for long-duration timers
- `swtmr` shell output reports wrong remaining cycles
- Applications relying on remaining-time queries for scheduling or watchdog logic may behave incorrectly

## Suggested Fix

Remove the narrowing cast:

```diff
 UINT64 OsSortLinkGetTargetExpireTime(UINT64 currTime, const SortLinkList *targetSortList)
 {
     if (currTime >= targetSortList->responseTime) {
         return 0;
     }
-    return (UINT32)(targetSortList->responseTime - currTime);
+    return targetSortList->responseTime - currTime;
 }
```

- Rerun the standalone reproducer in `testsuites/unittest/pbt/bug1_timer_trunc_pbt.c`
- Verify `timer_gettime()` for a timer whose remaining duration exceeds `UINT32_MAX / cycle_hz`
