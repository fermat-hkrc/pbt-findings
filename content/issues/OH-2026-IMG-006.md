## Summary

`HalfToFloat` unpacks IEEE-754 binary16 for `RGBA_F16` pixels, but applies a
normals-only exponent-rebase add `((mag << 13) + 0x38000000)` to **every**
input. For exact half ±0 the magnitude bits are 0, so the add invents float
bits `0x38000000` → `2^-15` (≈3.05e-5) instead of `0.0f`. Half zero (pure
black / fully transparent alpha) decodes to a non-zero float; sign is OR-ed
after, so `-0` becomes `−2^-15`. Not High: `HalfToUint32`'s
`static_cast<uint32_t>` usually truncates the tiny value back to 0, masking
the bug on 8-bit converts; float consumers see the wrong value. Pair of the
encode-side zero hole `FloatToHalf(0.0f) → 0x4000` (2.0). Confirmed and fixed
by developers (`DTS2026081424330`).

## Vulnerable Code

`frameworks/innerkitsimpl/converter/include/pixel_convert.h` — `HalfToFloat`
(~165):

```cpp
static inline float HalfToFloat(uint16_t ui)
{
    uint32_t u32 = ((ui & MAX_15_BIT_VALUE) << SHIFT_HALF_BIT) + SHIFT_HALF_MASK;
    //     (mag << 13) + 0x38000000   — normals-only bias fix (half 15 → float 127)
    u32 |= ((ui & SHIFT_16_MASK) << SHIFT_16_BIT);
    return UintToFloat(u32);
}
```

For half ±0 the magnitude is 0: `(0 << 13) + 0x38000000 = 0x38000000`
→ float `2^-15`. Zero has no normal exponent; the rebase add must not run.

Callers: `HalfToUint32` → `RGBAF16Convert*` in `pixel_convert.cpp` (~937);
`HalfTranslate` → pixel float reads / `AlphaF16ToUInt8` in `pixel_map.cpp`
(~4017); `jpeg_encoder.cpp` (~347) plane decode.

## Trigger Conditions

1. Input half is exact `+0` (`0x0000`) or `−0` (`0x8000`) — black /
   transparent samples are common live values.
2. `HalfToFloat` runs the rebase add on the zero magnitude.
3. Any float-domain consumer reads the result.

## Impact

- Half `0x0000` (black / transparent) decodes to `2^-15`, not `0.0f`.
- Float readers (`HalfTranslate`, jpeg plane decode) see non-zero samples.
- `HalfToUint32` → `static_cast<uint32_t>` often truncates back to 0 — masks
  the bug on the 8-bit path only.
- Medium: silent wrong float decode; exact-zero checks fail.

## Minimal Counterexample

| Input half | Expected float | Actual float | Actual bits |
|-----------:|---------------:|-------------:|------------:|
| `0x0000` (+0) | `+0.0` | **`≈3.05176e-5` (`2^-15`)** | **`0x38000000`** |
| `0x8000` (−0) | `−0.0` | **`≈−3.05176e-5`** | **`0xB8000000`** |
| `0x3C00` (control) | `1.0` | `1.0` | OK |
| `0x4000` (control) | `2.0` | `2.0` | OK |

## Suggested Fix

Early-return IEEE ±0.0f when the half magnitude is 0 (skip the rebase add):

```diff
 static inline float HalfToFloat(uint16_t ui)
 {
+    // ±0 half (mag == 0): do not run the rebase add (0 + 0x38000000 → 2^-15).
+    if ((ui & MAX_15_BIT_VALUE) == 0) {
+        uint32_t sign = static_cast<uint32_t>(ui & SHIFT_16_MASK) << SHIFT_16_BIT;
+        return UintToFloat(sign);  // +0 → 0.0f, -0 → -0.0f
+    }
     uint32_t u32 = ((ui & MAX_15_BIT_VALUE) << SHIFT_HALF_BIT) + SHIFT_HALF_MASK;
```

After fix: `HalfToFloat(0x0000) == 0.0f`, `HalfToFloat(0x8000) == -0.0f`;
normal path unchanged.
