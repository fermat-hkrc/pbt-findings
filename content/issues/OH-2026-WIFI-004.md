## Summary

`MessageQueue::DeleteMessageFromQueue` walks the timer list and unlinks every
node whose `messageName` matches. The loop advances **twice** on a hit, so the
node after a deleted match is never tested. One isolated match is removed.
**Two or more consecutive same-name nodes** leave a residue. The function
always returns `true`.

`StopTimer(name)` is this delete. After it returns, no queued message with
that name may remain, and every other message keeps its time order.

Confirmed and fixed under `DTS2607070006622`.

## Vulnerable Code

`wifi/base/state_machine/src/message_queue.cpp` — `DeleteMessageFromQueue`
(~105–130):

```cpp
InternalMessagePtr pCurrent = pTop;
while (pCurrent != nullptr) {
    InternalMessagePtr pPrev = pCurrent;      // predecessor = this node
    pCurrent = pCurrent->GetNextMsg();        // look at the *next* node
    if ((pCurrent != nullptr) && (pCurrent->GetMessageName() == messageName)) {
        InternalMessagePtr pNextMsg = pCurrent->GetNextMsg();
        pPrev->SetNextMsg(pNextMsg);
        MessageManage::GetInstance().ReclaimMsg(pCurrent);
        pCurrent = pNextMsg;                  // advance again — skip pNextMsg
    }
}
```

The loop never tests the node it starts an iteration on. After a delete the
next iteration starts **on** the successor, then immediately walks off it.

`A → X1 → X2 → B`, delete `X`:

| Iter | `pPrev` | `pCurrent` | Action | List |
|------|---------|------------|--------|------|
| 1 | `A` | `X1` | unlink `X1`, `pCurrent = X2` | `A → X2 → B` |
| 2 | `X2` | `B` | `X2` never tested | `A → X2 → B` |

Non-adjacent matches still work: after one delete the next node is not a
match, so the extra advance does not skip another hit.

## Trigger Conditions

`Handler` builds a `MessageQueue` only under `OHOS_ARCH_LITE`. Non-lite uses
`WifiEventHandler::RemoveAsyncTask` — this function is not on that path.

On lite, `StopTimer(name)` hits this when two or more still-queued messages
with that name sit **next to each other**. `AddMessageToQueue` inserts
equal-time messages at the head, so a second `StartTimer` of the same name
while the first is still queued makes a consecutive run.

Not a crash.

## Impact

- A stopped timer name can still fire: `GetNextMessage` returns the leftover
  same-name node.
- Other names keep their relative order; only the skipped sibling is wrong.
- High: live lite `StopTimer` path, always reports success.

## Minimal Counterexample

```cpp
MessageQueue q;
q.AddMessageToQueue(mk('A', 1), 1);
q.AddMessageToQueue(mk('X', 2), 2);
q.AddMessageToQueue(mk('X', 3), 3);
q.AddMessageToQueue(mk('B', 4), 4);
q.DeleteMessageFromQueue('X');
// expected GetNext: A, B
// actual:           A, X, B
```

## How PBT Detected This

`pbt-native/message_queue_delete_pbt_test.cpp` (real `message_queue.cpp`).
Oracle: a vector that inserts the same way `AddMessageToQueue` does, then
erases every item with that name.

| Property | Before |
|----------|--------|
| `DeleteRemovesAllMessagesWithThatNameAndPreservesOthers` | FAIL |
| `MixedAddDeleteGetMatchesSimpleModel` | FAIL |
| `ConsecutiveSameNameDeletesLeaveNoResidue` | FAIL |

## Suggested Fix

Carry a real predecessor. Advance once per node. Handle the head in the same
loop (`pPrev == nullptr`):

```cpp
InternalMessagePtr pCurrent = pTop;
InternalMessagePtr pPrev = nullptr;
while (pCurrent != nullptr) {
    if (pCurrent->GetMessageName() == messageName) {
        InternalMessagePtr pNextMsg = pCurrent->GetNextMsg();
        if (pPrev == nullptr) {
            pMessageQueue = pNextMsg;
        } else {
            pPrev->SetNextMsg(pNextMsg);
        }
        MessageManage::GetInstance().ReclaimMsg(pCurrent);
        pCurrent = pNextMsg;
    } else {
        pPrev = pCurrent;
        pCurrent = pCurrent->GetNextMsg();
    }
}
return true;
```
