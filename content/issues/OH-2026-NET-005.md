## Summary

`IpParamParser::GetIp4AndMask` expands a MULTIPLE_IP start–end range to CIDRs
with `while (startIpInt <= endIpInt)` and `startIpInt += (1 << cidrBits)`. When
the range ends at `255.255.255.255` (`0xFFFFFFFF`), the last step wraps to `0`
and the loop condition never fails → **deterministic infinite loop** on
netfirewall bitmap insert.

Same hang class as fixed `RfindIp6` (OH-2026-NET-004 / DTS2026072750511). Not
High: needs end literally all-ones; SINGLE_IP unaffected; not memory OOB.
Sibling orthogonal defect in the **same function** — signed `1 << 32` when
start is `0.0.0.0` — folded into this DTS. Confirmed and fixed by developers
(`DTS2026080608464`).

## Vulnerable Code

`services/netmanagernative/bpf/src/bitmap_manager.cpp` — `GetIp4AndMask`
(~510–528):

```cpp
while (startIpInt <= endIpInt) {          // both uint32_t
    // ...
    startIpInt += (1 << cidrBits);        // last step: 0xFFFFFFFF + 1 → 0
}
// 0 <= 0xFFFFFFFF → true forever
```

Caller: `BitmapManager::InsertIp4SegBitmap` (~205) — MULTIPLE_IP start–end →
CIDR list. Parcel carries start/end with no end≠all-ones ban.

Root cause: no overflow check on `startIpInt += block` when
`block > UINT32_MAX - startIpInt`.

Sibling (same function / same patch): zero-start `1 << 32` shift UB when
`cidrBits >= 32`.

## Trigger Conditions

1. Netfirewall **MULTIPLE_IP** IPv4 range rule with `end == 255.255.255.255`
   (or a last block that lands on that address with wrap).
2. `InsertIp4SegBitmap` → `GetIp4AndMask` runs the step loop.
3. Last step wraps `startIpInt` to `0`; `start <= end` stays true forever.

Unaffected: SINGLE_IP; ranges ending at `…254` or any non-all-ones end;
interior ranges that never step past all-ones.

## Impact

| Claim | Honest |
|-------|--------|
| High / always hang netsys | **No** — only MULTIPLE_IP with **end = 255.255.255.255** |
| UB (wrap path) | **No** — defined unsigned wrap |
| Every firewall rule | **No** — SINGLE_IP OK; ranges not ending at all-ones OK |
| Still a real bug | **Yes** — hang on that rule install path |
| Why Medium | Same as fixed RfindIp6: hang needs a specific range shape |

## Minimal Counterexample

```
start = end = 255.255.255.255  (0xFFFFFFFF)
suffixZeros = 0, block = 1, AddIp(/32)
startIpInt += 1 → 0
while (0 <= 0xFFFFFFFF) → infinite
```

| Range end | Loop |
|-----------|------|
| `…–255.255.255.255` | **hang** |
| `…–255.255.255.254` | OK |
| interior ranges | OK |

## How PBT Detected This

Algorithm witness / budgeted host loop (no production `.o` linked); verbatim
production loop at `bitmap_manager.cpp:521–528`:

| Case | Result |
|------|--------|
| `start=end=0xFFFFFFFF` | **hang** |
| `…254` end | OK |
| last `/24` ending all-ones | **hang** |

## Suggested Fix

Pre-add overflow break; pair with unsigned/`≥32` handling for the shift-UB
sibling in **one** patch:

```cpp
uint32_t block = (cidrBits >= 32) ? 0u : (1u << cidrBits);
AddIp(startIpInt, IPV4_BIT_COUNT - cidrBits, list);
if (block == 0 || startIpInt > UINT32_MAX - block) {
    break;
}
startIpInt += block;
```
