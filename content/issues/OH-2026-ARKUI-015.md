## Summary

When `dot(this, q) < 0`, `Slerp` flips **`from`** (`*this`) for the short arc.
At `t=0` the interpolant is then `−this`, not `this`. q and −q are the same
rotation, so matrices still match; sign-sensitive 4-vector consumers see a flip.

**Closed as non-issue** under `DTS2026091029544`: maintainers replied that (1) the `from` / `−from` result does not affect rendering and the 4-vector is not returned to developers, and (2) the code is ported from [Chromium's `quaternion.cc`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/ui/gfx/geometry/quaternion.cc), intentionally kept consistent with it, and will follow Chromium upgrades. The `Slerp(from, to, 0) == from` property is a valid Chromium-port contract (it fails on upstream Chromium too), but the endpoint flip is not product-visible and divergence from the port source is rejected as policy.

## Contract

Header: t∈[0,1] interpolates between this and q. Cited euclideanspace: 0.0 at
from. `from.Slerp(to, 0.0)` equals `from` component-wise.

## Vulnerable Code

```cpp
if (cosHalfAngle < 0.0) {
    from = from.flip();   // flips the t=0 endpoint
}
```

## Minimal Counterexample

`from=(-0.5,-0.5,-0.5,-0.5)`, `to=(0,0,0,1)`, `t=0` → `+from` (expected `from`).

## How PBT Detected This

`TZeroEqualsThis` FAIL; `TZeroSameRotation` PASS.

## Suggested Fix

Flip **`to`**, not `from`: `return Slerp(to.flip(), t);`.
