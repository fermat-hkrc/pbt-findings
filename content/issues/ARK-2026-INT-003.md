## Summary

`panda::helpers::string::ParseInt` clears `errno = 0` before calling `strtoll`
but never reads `errno` afterwards. On overflow, `strtoll` saturates to
`LLONG_MAX` / `LLONG_MIN` and sets `errno = ERANGE`. When `T` is the widest
type (`long long` / `intmax_t`), the function's own `min`/`max` defaults are
the type limits, so the post-parse range check `result < min || max < result`
cannot fire — the function returns `true` with the saturated value, reporting
a successful parse of an out-of-range input.

## Contract

POSIX `strtoll`: on range error it returns `LLONG_MAX` / `LLONG_MIN` and sets
`errno = ERANGE` — this is **not** a successful parse. `ParseInt` already
clears `errno` and requires full consumption (`*end == '\0'`); to honor the
contract it must also reject `errno == ERANGE`.

Caller `ParseNumericId` (`numeric_id.h:48`) parses into `intmax_t` with
`min = 0` and treats `false` as `"Invalid id"` — with the bug, a saturated
`LLONG_MAX` is accepted as a valid inspector script / breakpoint / frame /
object id.

## Vulnerable Code

`libpandabase/include/libpandabase/utils/string_helpers.h` (~73–101):

```cpp
errno = 0;
char *end = nullptr;
long long int result = strtoll(str, &end, base);
//                                              ^^^^^^^^^^^^^^^^^^^^^
//                                              BUG: errno never read — ERANGE ignored
if (str == end || *end != '\0') { errno = EINVAL; return false; }
if (result < min || max < result) { errno = ERANGE; return false; }
*num = static_cast<T>(result);
return true;
```

`strtoll` has already written both `ERANGE` and the saturated value. The
range check cannot see past the destination type's own limits, so for
`T = long long` it is dead code on overflow.

## Root Cause

The error channel of `strtoll` (`errno == ERANGE`) is unchecked. The
`min`/`max` clamp catches overflow only for **narrower** destination types
(e.g. `int32_t`); for the widest type the clamp coincides with the saturation
value and never rejects.

## Minimal Counterexample

```cpp
long long out = 7;
ParseInt(std::string("10000000000000000000"), &out);  // true; out == LLONG_MAX (expected: false, out unchanged)
ParseInt(std::string("9223372036854775808"), &out);   // true; out == LLONG_MAX (LLONG_MAX + 1)

int32_t out32 = 7;
ParseInt(std::string("2147483648"), &out32);          // false (narrow T already caught by min/max)
```

## When the Bug Triggers

Any decimal (or hex) literal whose magnitude does not fit in `long long`,
parsed with `T = long long` / `intmax_t` (default `min`/`max`). Narrow `T`
is unaffected. Not a crash: the parser reports success and hands back a
saturated value.

## Why Existing Tests Missed It

No in-tree gtest exercised `ParseInt` with an out-of-`long long`-range
decimal against the widest instantiation. Existing coverage used narrow
types (where the `min`/`max` clamp passes) or in-range values.

## How PBT Detected This

`libpandabase/tests/parse_int_pbt_test.cpp` — real header under test;
oracle is an independent `strtoll` run with `errno == ERANGE` (differential):

| Property | Result |
|----------|--------|
| `DecimalToStringRoundTrip` / `OutOfRangeRejected` (`int32_t`) | PASS |
| `LongLongOverflowRejected` | **FAIL** — `"10000000000000000000"` accepted |
| `LongLongOverflowSaturates` | FAIL — out-param overwritten, not left intact |
| `SignedHexAgreesWithStrtoll` / leftover / hex | PASS |

Serial reconfirm: `PBT_TEST_JOBS=1`.

## Impact

- Exported public header (`libpandabase/utils/string_helpers.h`); inspector
  id path (`ParseNumericId` → `inspector_server.cpp`) accepts saturated
  `LLONG_MAX` as a valid id instead of `"Invalid id"`.
- Silent wrong-value success — no crash, no error signal.

## Fix

Read the `errno` that is already cleared before the call:

```cpp
long long int result = strtoll(str, &end, base);
if (errno == ERANGE) {
    return false;
}
```

**Status: fixed upstream** — commit `bf74c199ec` "Fix ParseInt overflow
handling" (merged via `!14824 merge fix/parseint-overflow into master`)
adds exactly this guard at `string_helpers.h:89`. Local tree shows the fix.
