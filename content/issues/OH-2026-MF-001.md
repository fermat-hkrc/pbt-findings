## Summary

`Format::Stringify` SIGSEGVs on any format that holds a value stored via the
public setter `PutIntBuffer`. Two cooperating defects in `src/meta/format.cpp`
cause it:

1. **`GetValueType` misclassifies `std::vector<int32_t>`.** It has an explicit
   branch for `std::vector<uint8_t>` (→ `FORMAT_TYPE_ADDR`) but none for
   `std::vector<int32_t>` — the exact type `PutIntBuffer` stores. The unmatched
   type falls into the `else` branch, which returns `FORMAT_TYPE_INT32`.
2. **`Stringify`'s `FORMAT_TYPE_INT32` case dereferences a type-mismatched
   `AnyCast`.** It runs `std::to_string(AnyCast<int32_t>(iter->second))`. The
   value-overload `AnyCast` does `auto ptr = AnyCast<U>(&other); return *ptr;`
   — the pointer overload returns `nullptr` on a type mismatch, so `*ptr` is a
   null dereference → undefined behavior.

Manifestation is UB-dependent: the default build **SIGSEGVs** (exit 139); an
AddressSanitizer `-O1` build silently misreads near-null memory and emits
garbage (e.g. `result: [k = 19264 | ]`) instead of crashing. Introduced in
commit `58ca966e4` (2025-06-11) when `PutIntBuffer` was added without a matching
`GetValueType` branch.

## Contract

A Format holding any value storable through the public API must render safely.
`PutIntBuffer` is a public setter, so:

> ∀ key, ∀ n ≥ 1, ∀ data ∈ int32^n.
> `f.PutIntBuffer(key, data, n)` ⇒ `f.Stringify()` terminates without fault.

## Vulnerable Code

`src/meta/format.cpp` — `GetValueType` (misclassification) and `Stringify`
(null deref):

```cpp
// PutIntBuffer stores std::vector<int32_t>:
std::vector<int32_t> value(addr, addr + size);
meta_->SetData(key, value);

// GetValueType has a branch for vector<uint8_t> but NOT vector<int32_t>:
// unmatched type falls into the else → returns FORMAT_TYPE_INT32

// Stringify's FORMAT_TYPE_INT32 case:
std::to_string(AnyCast<int32_t>(iter->second));
// AnyCast value-overload (interface/inner_api/meta/any.h):
//   auto ptr = AnyCast<U>(&other);  // nullptr on type mismatch
//   return static_cast<ValueType>(*ptr);  // null deref → UB / SIGSEGV
```

`GetFormatMap()` (`MEDIA_OHOS`) shares the same misclassification; `Stringify`
is where it becomes SIGSEGV. Note that `Meta::GetValueType` already has a
`vector<int32_t>` branch — `Format::GetValueType` does not, which explains
passing Meta tests alongside a failing dump path.

## When the Bug Triggers

A key stored via `PutIntBuffer` / `OH_AVFormat_SetIntBuffer`, then
`Stringify()` or `OH_AVFormat_DumpInfo()`.

| Path | Reachable? |
|------|------------|
| **NDK** (`OH_AVFormat_SetIntBuffer` + `OH_AVFormat_DumpInfo` → `Stringify`) | **Yes** — third-party apps can crash without any in-repo engine code. |
| engine / plugin / scene | No production `PutIntBuffer` callers in this tree. |
| In-tree tests | `PutIntBuffer` tested with parcel/`GetData` only; `Format_DumpInfo_*` never uses IntBuffer. |

Report is **valid** as an SDK-reachable crash (latent in-tree until IntBuffer +
dump are combined). Severity is High (SDK / latent in-tree), not "all pipelines
already crash."

## Minimal Counterexample

RapidCheck cannot shrink a SIGSEGV (it does not intercept fatal signals), so the
witness is hand-derived to the minimal input: **one key, one int32 element**.

```cpp
Format f;
int32_t v = 42;
f.PutIntBuffer("k", &v, 1);
// f.GetValueType("k") returns FORMAT_TYPE_INT32 (== 1)
// for a key that actually holds std::vector<int32_t>
(void)f.Stringify();   // SIGSEGV (exit 139)
```

## How PBT Detected This

Property suite `pbt-native/format_stringify_pbt_test.cpp`:

| Property | Result |
|---|---|
| empty-format | PASS |
| INT32 exact format | PASS |
| STRING exact format | PASS |
| entry-count + determinism | PASS |
| `StringifyPbt.SurvivesIntBufferEntry` | **FAIL (SIGSEGV)** |

The crash-only contract asserts that any format populated via the public API
must survive `Stringify`. Four sibling properties pass; the IntBuffer case is
the sole failure. Minimal deterministic reproducer:
`pbt-native/repro_stringify_intbuffer.cpp`.

## Impact

- **Crash / DoS** when a format with an IntBuffer entry is dumped
  (`Stringify` / `DumpInfo` / `OH_AVFormat_DumpInfo`). Deterministic; low
  hit rate in-tree until IntBuffer + dump are combined, but **reachable from
  the NDK** without any in-repo engine code.
- **Silent data corruption** under toolchains/build flags that survive the UB:
  `Stringify` emits a bogus integer for the buffer entry instead of a
  `bufferSize = N` line, so logs mislead debugging.

## Suggested Fix

Two options (ideally both):

1. **Teach `GetValueType` about `std::vector<int32_t>`** — add an
   `IsSameTypeWith<std::vector<int32_t>>` branch returning a dedicated type
   (e.g. extend `FormatDataType` with `FORMAT_TYPE_INT32VECTOR`, mirroring the
   existing `FORMAT_TYPE_ADDR` for `vector<uint8_t>`), and handle it in both
   `Stringify` and `GetFormatMap`.
2. **Make `Stringify` defensive** — render via the `FORMAT_TYPE_ADDR` style
   (`key, bufferSize = N | `) when the Any is any vector type, and/or have the
   value-overload `AnyCast(const Any&)` throw `BadAnyCast` (its documented
   contract) instead of dereferencing null, so a misclassification surfaces as
   a catchable exception rather than a segfault.

The second fix (turning the null deref into the documented `BadAnyCast`) closes
the UB hole independently of the type-tag fix. `Meta::GetValueType` already has
the `vector<int32_t>` branch — mirroring that into `Format::GetValueType` is the
minimal type-tag fix.
