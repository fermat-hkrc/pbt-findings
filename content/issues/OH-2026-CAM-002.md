## Summary

`MultiBeautyType::SwitchBeautyValToDataShareVal` interpolates a beauty value across a discrete ability range using `range.size() - 1` as an integer divisor. When the ability range contains exactly **one** element (`range.size() == 1`), the divisor is `0`, causing integer division by zero → **SIGFPE** / process abort on x86 (undefined behavior generally). The single-element case is reachable: nothing upstream requires `|range| >= 2` before interpolation runs.

## Vulnerable Code

`services/camera_service/src/hcapture_session.cpp` (~257) — `SwitchBeautyValToDataShareVal`:

```cpp
valbasePlaceDiff = std::distance(range.begin(), it) * (PER_BEAUTY_VAL_NUM - 1) /
    static_cast<int32_t>(range.size() - 1) - valbasePlaceOld;
```

When `range.size() == 1`, `static_cast<int32_t>(range.size() - 1)` evaluates to `0`. `std::find` succeeds for the sole element, so the division executes unconditionally — there is no `range.size() <= 1` guard.

## When the Bug Triggers

A single-element ability range can occur and is sufficient to hit the divide-by-zero once `beautyVal` matches the sole ability entry. The defect is **not** blocked upstream:

| Layer | Prevents `range.size() == 1` from reaching the divide? |
|-------|--------------------------------------------------------|
| `GetBeautyRangeByType` | **No** — copies every `item.count` entry; `count == 1` → `range` has one element. |
| `CaptureSession::GetSupportedBeautyRange` | **No** — exposes that one-element vector to apps when `count == 1`. |
| `SetBeautyValueByType` (persist) | **No** — if `beautyVal` is that single level, call proceeds to `SwitchBeautyValToDataShareVal` (~1277). |
| `UpdateBeauty` | **No** — type check only; no minimum range size. |
| `SwitchBeautyValToDataShareVal` | **Bug here** — divides by `range.size() - 1` with no `range.size() <= 1` guard. |

Multi-step sliders are common in shipping HALs, so `item.count == 1` is likely rare in the field — that affects how often the bug fires, not whether the code allows the trigger. The reverse mapper `SwitchDataShareValToBeautyVal` already supports `|range| == 1` without dividing (uses `range.size() - 1` as a *multiplier*), which shows single-element ability metadata is intentional in this feature.

## Minimal Counterexample

| Field | Value |
|-------|-------|
| type | `SKIN_SMOOTH` (`kTypeMin`) |
| `range` | `{3}` (size 1) |
| `beautyVal` | `3` (in range) |
| Result | **SIGFPE** / process abort (not a return code) |

```cpp
std::vector<int32_t> range = {3};   // ability advertises exactly one level
// SwitchBeautyValToDataShareVal(device, type, /*beautyVal=*/3, range, ...)
//   std::find(range, 3) succeeds → division by range.size() - 1 == 0 → SIGFPE
```

## How PBT Detected This

A RapidCheck property (`SwitchBeautyValPbt.SingleElementRangeMustNotCrash`) encoded the negative/safety contract: for a supported beauty type and a device whose ability range contains exactly one value, calling `SwitchBeautyValToDataShareVal` must not throw and must return `CAMERA_OK` or `CAMERA_INVALID_ARG` — never crash. RapidCheck shrank the input to `type=SKIN_SMOOTH`, `range={3}`, `beautyVal=3`. A complementary `EXPECT_DEATH` death test documents the current crash.

```cpp
RC_GTEST_PROP(SwitchBeautyValPbt, SingleElementRangeMustNotCrash,
    (const BeautyType& type, const std::vector<int32_t>& range, int32_t beautyVal))
{
    if (range.size() != 1 || range[0] != beautyVal) RC_DISCARD();   // target the one-element case
    int32_t rc = SwitchBeautyValToDataShareVal(device, type, beautyVal, range, ...);
    RC_ASSERT(rc == CAMERA_OK || rc == CAMERA_INVALID_ARG);   // must not crash
}
```

## Impact

The bug lives in the capture-session beauty path. When triggered it aborts the process via SIGFPE (x86); on platforms that do not trap divide-by-zero it is undefined behavior with no observable guarantee. Likelihood is low–moderate: many HALs ship 2+ beauty steps, but a single advertised beauty level is valid metadata the framework exposes via `GetSupportedBeautyRange`, so the path is reachable rather than hypothetical.

## Suggested Fix

Before using `range.size() - 1` as a divisor, treat `|range| <= 1` as a **fixed point** — no interpolation between discrete ability levels. Set `valbasePlaceDiff = 0` and continue with the existing clamp/update of `shareVal`. This mirrors the reverse mapper, which already uses `range.size() - 1` as a multiplier (safe when size is 1).

```diff
### services/camera_service/src/hcapture_session.cpp
@@ -252,8 +252,14 @@ static int32_t SwitchBeautyValToDataShareVal(const sptr<HCameraDevice>& device,
     if (it == range.end()) {
         MEDIA_ERR_LOG("SwitchBeautyValToDataShareVal failed, beautyVal:%{public}d not support", beautyVal);
         return CAMERA_INVALID_ARG;
     }
-    valbasePlaceDiff = std::distance(range.begin(), it) * (PER_BEAUTY_VAL_NUM - 1) /
-        static_cast<int32_t>(range.size() - 1) - valbasePlaceOld;
+    if (range.size() <= 1) {
+        valbasePlaceDiff = 0;
+    } else {
+        valbasePlaceDiff = std::distance(range.begin(), it) * (PER_BEAUTY_VAL_NUM - 1) /
+            static_cast<int32_t>(range.size() - 1) - valbasePlaceOld;
+    }
     valbasePlaceDiff = std::clamp(valbasePlaceDiff, -PER_BEAUTY_VAL_NUM + 1, PER_BEAUTY_VAL_NUM - 1);
     shareVal += valbasePlaceDiff * basePlaceVal;
     shareVal = std::clamp(shareVal, 0, g_beautyShareMax);
```

The same guard is mirrored in `pbt-native/switch_beauty_val_real.cpp` (the verbatim extract the harness builds against). A `try/catch` or SIGFPE handler was rejected — it does not fix the logic error and still leaves UB on platforms that do not trap. Rejecting single-element ranges at `GetBeautyRangeByType` was also rejected: a single advertised level is valid metadata the framework already exposes.
